# SDTM 適合性指摘の仕分け

CDISC CORE は数万件の指摘を出すことがある。件数の多い指摘に新規の指摘が埋もれるので、
ルール単位で「直す」「既知として残す」を決めて記録に落とす。

以下 `$SKILL` は**このSKILL.mdが置かれているディレクトリの絶対パス**。symlink 経由で
読み込まれていても実体のディレクトリを解決して使う。

## 手順

この順で進める。**4 を後回しにしない。** 実データの集計から仕様を推測すると遠回りになる。
CRF を見れば項目の作りが分かり、答えが一度に出ることが多い。

1. ルールの定義を読む（何を条件にしているか）
2. 指摘の内訳を集約する（件数を原因ごとに分解する）
3. 実データで再現する（ルールの条件を自分で当てて、件数が一致するか見る）
4. **Annotated CRF を読む**（その項目が CRF でどう尋ねられているか）
5. 解析での使われ方を確認する（ADaM・ARD がその変数を使っているか）
6. 直す／既知として残すを決めて CSV に書く
7. 直す場合は両系（SAS・R）に独立に実装し、突合で確認する

## 1. ルールの定義を読む

CORE のメッセージは「必須の TSPARMCD が不足」までしか言わず、何が足りないかを示さない。
キャッシュの `rules.pkl` は core_id をキーにした dict で、`conditions` に条件が入っている。

```python
import pickle, json
d = pickle.load(open(r'%USERPROFILE%\opt\cdisc-core\core\resources\cache\rules.pkl', 'rb'))
r = d['CORE-000914']
print(r['sensitivity'], r['description'])
print(json.dumps(r['conditions'], ensure_ascii=False, indent=1))
print(json.dumps(r.get('datasets'), ensure_ascii=False))     # 他ドメインを参照するか
```

見るべき点。

- `sensitivity` … `Record` なら1行1件、`Dataset` ならデータセット単位で1件。**`Dataset` の
  ルールは指摘1件でも実データでは何百行も該当することがある**（実測で `CORE-000118` は
  1件の報告に対し実データ772行）
- `conditions` … `all`/`any` の構造と、比較対象の変数
- `datasets` … 他ドメインを参照するルールか（`RELREC` を経由するものがある）
- グルーピングキー … 一意性を見るルールは `comparator` にキーの一覧が入る。**そのキーが
  対象ドメインの構造に合っているか**を確かめる（FA では `FAOBJ` が観測の対象なのに、キーに
  含まれないルールがある）

**メッセージだけを手がかりに推測で埋めない。**

## 2. 指摘の内訳を集約する

```bash
python "$SKILL/scripts/summarize-core-issues.py" --report <日付>-sdtm-validation.json \
       [--disposition docs/core-issue-disposition.csv]
python "$SKILL/scripts/summarize-core-issues.py" --report ... --rule CORE-000914
```

`--rule` は指摘された変数と値の組み合わせを集約する。ここで見るべきこと。

- **1つのルールの指摘が複数の原因の混合であることがある。** 実測では FA のベースライン
  フラグの重複261件のうち、166行が CRF の構造で、95行はルールのキーに `FAOBJ` が入らない
  ことによる偽陽性だった。前者は直せるが後者は直せない
- **指摘の件数がドメインの全行数と一致したら、データの欠陥ではなくルールの前提を疑う。**
  スクリプトが警告を出す。実測では `CORE-000744` の15,291件が FA の全行で、原因は RELREC を
  持たないため親レコードを引けないことだった。IG の原文は「親レコードを持つ場合は」と
  条件付きだが、実装はその前提を持たない
- **指摘の件数が「あるシートの未実施件数」と一致したら、EDC の既定値を疑う**（4 を見る）
- `EXECUTION ERROR` のルールも `Issue_Summary` に各1件として現れる。指摘の件数に混ぜると
  誤る（実測で ISSUE REPORTED 31 に対し集計が35ルールになった）

## 3. 実データで再現する

ルールの条件を自分で当てて件数が一致するかを見る。一致しなければルールの読み方が違う。

一致したうえで、キーを変えて件数がどう変わるかを見ると原因が分解できる。

```python
# 例：ルールのキーと、それに観測の対象（FAOBJ）を足したキーで重複を数え分ける
k1 = Counter((r['USUBJID'], r['FATESTCD'], r['FACAT'], r['FASCAT']) for r in bl)
k2 = Counter((r['USUBJID'], r['FATESTCD'], r['FACAT'], r['FASCAT'], r['FAOBJ']) for r in bl)
# k1 の重複 261 行 − k2 の重複 166 行 = 95 行がキーの不足による偽陽性
```

## 4. Annotated CRF を読む

**受領データの構造に疑問が出たらここへ来る。** 「この変数はなぜ空なのか」「なぜ1症例2行
あるのか」は、CRF の項目の作りを見れば分かることが多い。

```bash
ls "<受領データ>/Annotated CRF <日付>/"          # シートごとに PDF が1つ
pdftotext -enc UTF-8 -layout "49.移植後療法：(開始時)試験薬投与報告.pdf" - | head -60
pdftotext -enc UTF-8 -layout "05.寛解導入療法：有害事象報告.pdf" - | grep -n "CMDUR\|CMOCCUR"
```

`-layout` を付けると項目名と SDTM 変数の対応注記が並んで出る。Ptosh の Annotated CRF は
項目の右側に落とし先の変数名（`CMDOSE`・`FAORRES when FATESTCD = AGVHD` など）を注記する
ので、どの項目がどの変数になるかが読める。

どのシートを見るかは `--SPID` が示す。Ptosh は CRF のシート名（acronym）を `--SPID` に
出すので、指摘された行の `--SPID` を見てから対応する PDF を開く。

実測で CRF を読んで初めて分かったこと。

- `CMPRESP='Y'` なのに `CMOCCUR` が空だったのは、CRF が「G-CSF投与日数」「血小板輸血投与量
  (総単位)」という数量の入力欄しか持たず、有無の選択肢が無かったため。同じシートの
  「ラスブリカーゼ投与 あり／なし」は選択肢なので `CMOCCUR` に値が入る
- `CMPRESP` も `CMOCCUR` も空だった11件は、CRF に3剤が印字されて投与量だけを入力する形で、
  投与量が入った薬剤だけレコードになるため `CMPRESP` が付かずに来ていた。自発報告ではない
- `FAOBJ='Hypertension'` が1症例2行あったのは、高血圧症治療と糖尿病治療が同じ項目群で
  収集され、SDTM 上の区別が収集順しか無かったため

**PDF が読めないときは開いて見てもらう。** `pdftotext` はレイアウトが崩れることがあり、
入力必須のマークや選択肢の有無は画像として見ないと分からない場合がある。

## 5. EDC 由来のパターン

EDC の入力効率化のための設計が、SDTM の変数の定義とずれることがある。繰り返し出る。

- **既定値が入っている。** ベースラインの結果を1枚のシートで集める運用では、フラグを後から
  付ける手間を省くため `--BLFL` に既定値の `Y` が入る。検査が行われなかったレコードにも
  残るので、`--STRESC` が欠測の行のフラグを落とす。実測で `LBBLFL='Y'` の4094行すべてが
  `LBSPID='baseline'` で、逆に `baseline` の4094行すべてに `Y` が立っていた（例外0）
- **項目の尋ね方が混在する。** 同じカテゴリの中に有無を選択させる項目と数量だけを入力させる
  項目がある。後者は `--OCCUR` が空で来るので数量から導出する（数量0が発生なし）
- **値が入力されなかった項目のレコードを出力しない機能がある。** Ptosh はこれを搭載して
  いる。`--ORRES` などに値が無い、つまり投与や実施が無かった項目はレコードそのものが出ない。
  **したがってレコードの不在は「行われなかった」を意味する。** 入力漏れと取り違えないこと。
  この機能があるため、事前規定の項目でも `--PRESP` が付かずに来ることがある。CRF に印字
  されているなら `Y` を補う。ただし**不在の項目のレコードを作って行数を揃えようとしない。**
  `--OCCUR='N'` を作る根拠は無く、不要なレコードを出さないのが正しい仕様である
- **同じ項目が別の意味で2度収集される。** 1つの `--OBJ` や `--TESTCD` に2種類の観測が入り、
  区別が収集順（`--SEQ`）しか無いことがある。SDTM 層で `--CAT` に区別を入れて、解析層が
  収集順に依存しないようにする

**処理は全ドメインに適用する。** 1つのドメインで見つかっても他でも起きる。出力の直前に
置くと漏れがない。落とした件数・導出した件数はログに出し、前提が崩れたら WARNING を出す。

横断の手順は試験のリポジトリではなく方法論の文書に書く（このスキルと、EDC ごとの手順書）。

## 6. 解析での使われ方を確認する

直す前に、その変数が ADaM・ARD で使われているかを見る。使われていなければ SDTM の正確さ
だけの問題で、解析の数字は動かない。使われていれば突合をやり直す。

```bash
grep -n "LBBLFL" program/*_SDTMtoADaM.sas program/r/*_SDTMtoADaM.R program/*_ARD.sas
grep -n "^adam,.*,LBBLFL," docs/variable-map.csv
```

同名の変数が別の意味で使われることがある。実測では ADAE の `AENDT`（AE の終了日）と
ADEC の `AENDT`（投与終了日）が別物で、ARD が使っていたのは後者だった。

## 7. 仕分けを CSV に持つ

`core_id,disposition,note,ref` の4列。`disposition` は `known`（判断が済んで対応しない）と
`open`（決まっていない）の2つで足りる。詳細は `ref` が指す文書に書き、`note` は1行にする。

検証スクリプトの集計でこの CSV を読み、既知・未仕分け・実行できなかったルールの3つに
分けて出す。未仕分けが減っていくことが進捗になる。

**CORE の `--exclude-rules`（`-er`）でルールを除外する形にはしない。** 除外すると何を
外したかが検証結果の JSON に残らず、データの設計が変わって指摘の性質が変わっても
気づけない。外部の提供先が自分で CORE を回せば同じ指摘が出るので、こちらで消しても
意味がない。検証は素のまま回して全件を JSON に残し、集計の段で分ける。

## 8. 直すときの実装

- 両系（SAS・R）に独立に実装する。同じ CSV や同じ判定表を読む形にして、変換だけを二重に
  書くと転記の誤りを突合で拾える
- 件数の自己チェックを入れる。前提（1症例2行など）が崩れたら WARNING を出す
- 受領値を書き換えるときは理由を仕様書に書く。「受領データをそのまま保つ」方針と衝突する
  ので、標準に合わせるために変えたことを残す
- 直したあとに全層（SDTM → ADaM → ARD）を回して突合し、解析の数字が動いていないことを
  確かめる

## 落とし穴

- **CORE を回すだけのスクリプトと、SDTM を作り直すスクリプトが別なことがある。** 変換を
  直したのに検証だけ回して「直っていない」と誤認する。パイプライン全体を回す
- **`core.exe validate --help` は日本語環境（cp932）で落ちる。** ヘルプ文に `█` が入って
  おり `UnicodeEncodeError` になる。`PYTHONIOENCODING` も `chcp 65001` も効かない。
  オプションの有無は `core.exe validate <オプション> X -d nosuchdir` を試して
  `No such option` が出るかで判定する（click が綴りの候補も出す）
- **指摘が減ったら別の指摘が増えることがある。** ラベルを IG に合わせると「title case で
  ない」が消えて「IG と一致しない」が立つ、といったトレードオフがある。件数が同じなら
  データの正しさで選び、理由を記録する
