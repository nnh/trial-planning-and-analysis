# 試験立案時のレビュー

解析が止まる原因は3つに分かれる。統計解析計画書の記述が実装に落とせる粒度でない、電子症例報告書の構造が解析の単位と合っていない、外部データの受領形式が決まっていない。いずれも解析の段階では直せない。計画書と症例報告書は固定済みで、直すには改訂手続きが要り、外部データは提供元との往復に数週間かかる。

ある試験では、解析中に人の判断を待って止まった箇所が40件あり、決着まで4日を要した。うち24件は立案時に決められたものだった。

## 正本はここに無い

チェックリストと機械検査の規則は公開リポジトリ `nnh/trial-planning-and-analysis` の `review/` が持つ。このスキルは順序と出力の形だけを持ち、規則を写さない。写すと正本が2つになり、片方だけ直された状態に必ずなる。

- 研究計画書 — `review/planning-review/checklist-prt.md`（9節）
- 図表案 — `review/planning-review/checklist-tlf-shells.md`（11節）
- 統計解析計画書 — `review/sap-review/checklist.md`（9観点）
- 電子症例報告書 — `review/ecrf-review/checklist.md`
- 過去に見つかった欠陥の型 — `review/planning-review/findings-log.md`・`review/ecrf-review/findings-log.md`

以下 `$SKILL` は本 SKILL.md が置かれているディレクトリの絶対パス。

## 1. 資料を集める

必須6点とあると通る4点は `ecrf-review/checklist.md`「1. 資料の収集」が正本。ここへ写さない。依頼から入手まで日数がかかるため、着手の2週間前には依頼を出す。

集めたら最初に版を並べる。すべて同じ時点のものであることを確かめる。統計解析計画書の作成日が研究計画書より前になっているような前後関係の矛盾は、それ自体が最初の指摘になる。

文書は機械検査にかけられる形にする。docx は `pandoc -t markdown`、Google Docs は markdown で書き出す。書き出しの経路で見出しと目次の形が変わるので、両方の形を検査が扱えることは確認済みである。

## 2. 機械検査を回す

```bash
python "$SKILL/scripts/run-planning-review.py" --sap <SAP.md> --prt <PRT.md> --ecrf <構造定義.json>
```

渡したものだけを検査する。既定は `--severity warning` で、判断が要るものに絞る。

規則が拾うものは各スクリプトの冒頭が持つ。文書は S01 から S10（目次と本文の不一致、節番号の重複と欠番、句点で終わらない段落、段落の重複、略号一覧、一度しか現れない図表番号、全角の英数字、編集メモの痕跡、メールアドレス）、構造定義は R01 から R12（シートグループ未割り当て、参照フィールドの参照先違い、TESTCD の長さ、選択肢の重複、バリデータの欠落など）。

**件数が0でも、検査が走ったことを確かめる。** 終了コードが0でなければ検査は途中で落ちており、0件と区別が付かない。実際に、変数名を持たないマッピングで異常終了し、以降の規則が1つも走らなかったことがある。

機械検査で0件でも設計が正しいことにはならない。以下は人が見る。

## 3. チェックリストで見る

対象ごとに正本のチェックリストを1つずつ当てる。順序は依存の向きに従う。

1. 研究計画書 — 版と改訂スコープ、文書としての整合性、法令と審査条件、解析が引く条文、適格基準の機械可読性、評価スケジュールと収集経路、関連文書との整合
2. 統計解析計画書 — `sap-review-checklist.md` の9観点。加えて統計手法の細目（信頼区間の算出法、時点信頼区間の形式、競合リスクの推定量、四分位点の定義、丸めと表示桁）が書かれているか
3. 図表案 — 逆引きの対応表、分母、行の項目と順序、水準の並びの決め方、セルの中身、列の構成と群、表題と表番号、評価時点、表示文言、収集との突合
4. 電子症例報告書 — 実データでの裏打ち、計画書と図表案との突合

図表案から本文への逆引きを最初に作る。ここで見つかる欠落が最も重く、個々の表を丁寧に見ても出てこない。

## 4. 指摘を出す

指摘ごとに次を書く。文章での説明だけにしない。修正を反映する人が判断だけで済む形にする。

- 該当箇所 — 文書名と節番号
- 問題点 — 何が起きるかまで書く。「定義が曖昧」ではなく「この定義を文字どおり適用すると Unfit 群が安全性解析から丸ごと落ちる」
- 修正前 — 現行の記載の引用
- 修正後（案） — そのまま貼れる文
- 対応先 — データセンターへの確認・研究計画書の改訂・統計解析計画書への明記・入力手引きへの記載のどれか

区分は重要・中程度・軽微の3つ。基準は、解析が成立しなくなるか、解釈が割れるか、表現の問題か。プログラム化を妨げるもの（分母が決まらない、条件が実在しない）を最優先に置き、表現の統一を最後に置く。

その文書種別で正常な状態を指摘にしない。図表案の `xx(%)` は実データを入れる前の枠として正しく、研究計画書の連絡先の節にメールアドレスがあるのも正常で、要旨の章を持つ計画書で概要と本文が同じ段落を繰り返すのも正常である。

## 5. 記録する

試験リポジトリの `docs/planning-review-YYYYMMDD.md` に残す。

- 検査対象（資料の版・日付・所在）
- 指摘（上の形式で、区分ごとに）
- 確認により解消した論点と、その理由

最後の「解消した論点」を消さない。同じ検査を次に回すと同じ項目が再び挙がるため、理由を残しておかないと毎回同じ照会を繰り返す。ある試験では初回に挙げた24件のうち11件がこれに当たった。自分の検査の誤りだったものも残す。

被験者単位の情報とメールアドレスの実体を、この文書に書かない。件数と所在で足りる。

積み残しを `action-items.md` に、未解決の論点を `issues.md` に転記する。

## 6. 枠組みへ返す

汎用化できる欠陥の型を `planning-review/findings-log.md`（文書側）と `ecrf-review/findings-log.md`（構造定義側）へ追記する。ここに書かなければ次の試験で同じ検査を思いつけない。

書き方は既存の記載に揃える。見出しは型の名前にし、症状ではなく原因で書く。本文は、何が起きたか・どう見つけるか・出どころ（試験名と日付、機械検査で拾ったなら規則番号）の順。

2試験目で同じ型が出たら、機械で判定できるか見る。できれば規則にして番号を足す。判断が要るならチェックリストの項目にする。

## 検出できないもの

このレビューで担保できるのは、文書が実装に落ちる粒度になっていることと、収集の設計が解析に足りることまでである。統計手法の妥当性、臨床的な妥当性、そしてデータそのものの正しさは担保できない。報告するときに混同しない。
