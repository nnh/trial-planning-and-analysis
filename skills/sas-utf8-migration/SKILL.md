# SAS の UTF-8 セッションへの移行

SAS 9.4 の日本語版は既定の config が shift-jis で、`.sas` も出力も CP932 になる。受領データ・R・Python・md が UTF-8 の環境では SAS だけが例外になり、層をまたぐたびに変換が要る。符号化の差は「静かに壊れる」形で出るので（列のずれ、値の切り捨て、並び順の違い）、移行は前後の成果物を突き合わせながら行う。

以下 `$SKILL` は**このSKILL.mdが置かれているディレクトリの絶対パス**。

方針の正本は組織内の SAS 環境ドキュメント「セッションの文字符号化」が持つ。実装の写し元は試験リポジトリの `scripts/sas-common.ps1`。

## 1. Unicode サーバーの有無を確かめる

再インストールは要らない。SAS 9.4 の導入時に Unicode サポートが入っていれば、config を指すだけで UTF-8 セッションになる。

```bash
ls "C:/Program Files/SASHome/SASFoundation/9.4/nls/"
```

`u8/` があればよい。`u8/sasv9.cfg` は `-ENCODING UTF-8 -DBCS -LOCALE ja_JP` を持つ。`-DFLANG` の行は無いが LOCALE から JAPANESE になるので、日本語の日付書式は従来どおり使える。`u8/` が無いときだけ SAS Deployment Wizard で Unicode サポートを追加する（製品の再インストールではない）。

## 2. 符号化の混在を洗う

```bash
python "$SKILL/scripts/scan-encoding.py" <ルート> [<ルート2> ...]
```

ソース（`.sas`）だけでなく、**入力データを必ず含める**。CP932 の CSV が1つ混ざっているだけで `proc import` が列をずらし、後続の変数に別の値が入る。ずれた列が数値なら「無効なデータ」の NOTE が出るが、文字なら黙って別の値が入るので気づけない。

見るもの。

- `.sas`・`.txt`・`.csv`・`.R`・`.py`・`.md`
- 受領データの置き場（試験ごとの `input/rawdata`・`input/ext`）
- 外部から受けるマスタ（施設・疾患・薬剤）。受領元が違うと符号化も違う

## 3. 移行前の成果物を凍結する

**移行の前に、いまのまま最初から最後まで通して成果物を保存する。** これをしないと、移行後に出た差が符号化のせいなのか元からそうだったのかを切り分けられない。

凍結するのは、値が機械で比べられるものを選ぶ。RTF や PDF は符号化そのものが変わるので比較の主役にしない。

- Dataset-JSON（層ごと）
- 集計値の CSV（ARD・図表のセル台帳）
- 配布用の CSV

## 4. ソースを変換する

```bash
python "$SKILL/scripts/convert-to-utf8.py" <ルート> --dry-run
python "$SKILL/scripts/convert-to-utf8.py" <ルート>
```

CP932 として読めて UTF-8 へ変換でき、**戻したときに元のバイト列と一致するものだけ**を変換する。一致しないものは変換せず報告するので、中身を見てから個別に決める。BOM は付けない（SAS は BOM 付き UTF-8 のソースを読めない）。

受領データを変換するときは原本の控えを別の場所へ取る。受領物を書き換えるのは、他に読み手がいないと分かっているときだけにする。

## 5. 起動を UTF-8 にする

```
sas.exe -config "C:\Program Files\SASHome\SASFoundation\9.4\nls\u8\sasv9.cfg" -sysin <program> ...
```

端末の既定 config は変えない。試験ごとに切り替えられる余地を残すためで、従来の shift-jis で回すときは `nls\ja\sasv9.cfg` を指す。

**ログを読む側の符号化も同時に変える。** CP932 のまま読むと `^ERROR` の検出が効かなくなり、失敗した実行が成功に見える。PowerShell なら `[IO.File]::ReadAllLines($log, (New-Object System.Text.UTF8Encoding($false)))`。

## 6. 前後の成果物を突き合わせる

```bash
python "$SKILL/scripts/compare-outputs.py" <移行前のフォルダ> <移行後のフォルダ>
```

生成日時の行は落として比べる。値が1つでも変わったら、それは符号化の問題ではなく実装の問題なので、そこで止めて原因を追う。

## 移行で必ず出るもの

**日本語の文字列で並べている箇所の並びが変わる。** CP932 は 無 96b3 < 有 974c、UTF-8 は 有 6709 < 無 7121。表の水準を表示名の照合順序で並べていると、日本語版の表だけ並びが変わる（英語版は変わらない）。値は変わらないので、比較は「値の多重集合は一致、行の位置だけ違う」形になる。

並びを確定させるには2つの道がある。新しい並びを正とするか、表示名に依らない順序番号を持たせるか。後者にすると符号化に依存しなくなるが、検証済みの出力を作り直すことになるので、表の見え方を決められる人の判断が要る。

**R 側で SAS の並びに合わせていたら外す。** CP932 のバイト列へ直してから並べる細工を入れている場合、SAS が UTF-8 になったら不要になる。R の `order(..., method="radix")` は UTF-8 のバイト順なので、そのままで揃う。

**日本語を入れる文字変数の `length` が足りなくなる。** UTF-8 は全角1文字3バイトで CP932 の1.5倍要る。`length x $10` に日本語6文字を入れると切れる。移行前に、日本語が入る文字変数の最大バイト長を測っておく。

```sas
b_utf8 = lengthn(kcvt(strip(x), 'sjis', 'utf8'));   /* CP932 セッションで測る */
```

CDISC の SDTM・ADaM は値を ASCII に寄せているので、この問題は自由記述を残している層（コメント・経過記述）と、表示名を持つ中間データに出る。

**`proc export` はセッションの符号化で書く。** UTF-8 セッションでは UTF-8 で出るので、CP932 前提で読んでいた下流があれば直す。逆に、CP932 の時代に `file ... encoding='utf-8'` を明示して回避していた箇所は、そのままで正しく動く。
