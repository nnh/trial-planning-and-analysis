# SDTM・ADaM の文字集合の検査と ASCII 化

日本の試験は CRF に日本語の自由記述欄があり、そのまま SDTM へ流すと非ASCIIの値が
提出データに混ざる。データ共有プラットフォームへの登録、海外ツールでの検証、
Shift_JIS を厳密に実装した処理系での読み込みで問題になる。

以下 `$SKILL` は**このSKILL.mdが置かれているディレクトリの絶対パス**。symlink 経由で
読み込まれていても実体のディレクトリを解決して使う。

## 1. まず検査する

```bash
python "$SKILL/scripts/check-nonascii.py" --root "<データルート>"
```

`--root` は `input/sdtm/json` と `input/ads/json` のうち存在するものを探す。二重コーディング
の試験でも、共有先が受け取るのは正本の側だけなので、検証用の並行実装（`sdtm_r` 等）は
既定に入れない。この構成でないとき、両方を見たいときは `--dir ラベル=パス` を並べる。
Dataset-JSON・CSV・sas7bdat を読む。**共有先が受け取るファイルで判定したいので、
Dataset-JSON があるならそれを対象にする**（sas7bdat では、書き出しの段階で起きる
変換の問題を見落とす）。

許容する変数があるときは `--allow DS.VAR` を並べる。許容の理由は呼び出し側の仕様書に
書き、スキルには書かない。オプションは `--help` が正本。

終了コードは、許容していない非ASCIIが1件でもあれば 1。CI やパイプラインの検査に
そのまま使える。

## 2. 出た値を層で分けて対処を決める

非ASCIIの値は出どころで3種類に分かれる。**同じ対処を全部に当てない**。

### CRF の選択肢・区分の値

`変異なし`・`予防投与` のような、選択肢や区分として決まった語。**識別子に置き換え、
表示名は別のカタログが持つ**。

- SDTM の `--ORRES` に英語表記、`--STRESC` に識別子を入れる
- ADaM は識別子を採る（`--ORRES` ではなく `--STRESC` を predecessor にする）
- 表示名（英語・日本語）はラベルカタログ（`docs/label-catalog.csv` 等）が持ち、
  TLF がそこから引く。define.xml の CodeList も同じカタログから作る
- **対応表を2箇所に書かない**。SDTM 作成プログラムと define.xml 生成スクリプトが
  同じカタログを読む
- **対応表に無い値が来たらプログラムを止める**。新しい値が黙って落ちるのを防ぐ
- 二重コーディングをしている試験では、片方（R系など）は対応表を独立に持たせる。
  両方が同じCSVを読むと、対応表の誤りを突合で検出できなくなる

### 派生変数のラベル・説明文

`ADLB.PARAM`・`ADTTE.EVNTDESC` のような、解析側で付けた日本語。**英語に直す**。
値そのものが解析ロジックの分岐に使われていることがある（イベント種別の文字列比較など）
ので、**分岐している箇所を先に洗い出し、SAS系とR系を同時に直して突合をやり直す**。

### 安全性報告・コメントの自由記述

SAE 報告書の経過記述（`CO.COVAL`）のような長文。**英訳ではなく、データセットから
切り離すことを先に検討する**。理由は3つある。

- 解析に使っていない。ADaM・TLF に出ないので、外しても成果物が変わらない
- 匿名化の対象になる。身長・体重・受診日・治療の詳細が原文のまま入っており、
  共有先の de-identification 要件では自由記述テキストの削除・加工が通例
- ICH E2B の安全性報告として集めたもので、解析に用いる観測データではない

切り離しの実装は次の形にする。

- SDTM ライブラリではなく別ライブラリ（`pv` 等）へ出す。Dataset-JSON 生成・
  define.xml 生成・突合の対象から自動的に外れ、除外リストを維持する必要がなくなる
- **ドメイン単位ではなく行の条件で分ける**。`CO` なら `RDOMAIN='AE'` の行だけを外し、
  他の `RDOMAIN` はデータレビューや解析に要る可能性があるので残す
- 分けた結果0行になるドメインは、データセット自体を作らない（空のドメインを
  define.xml に載せない）。条件が変われば自動的に復活する形にしておく
- 親レコードとの対応は `--SPID` が持つことを確認する。`AE.AESPID` と `CO.COSPID` が
  同値なら、`USUBJID` との組で一意に決まる。**SDTM の外に出したデータは RELREC では
  参照できない**ので、この対応を仕様書に明記して唯一の鍵にする。`SUPP--` に追加の
  変数は作らない
- PI・医師には読み物（HTML等）として提示する。見出しに親ドメインの変数
  （`USUBJID`・`--SPID`・MedDRA PT・発現日・Grade・重篤性・転帰）を出すと、
  一覧のどの行の話か迷わない
- 置き場を `.gitignore` で除外する。自由記述は private リポジトリでも履歴から
  消せなくなる

## 3. CP932 と Unicode の対応差

`cp932 で表せない文字` と `CP932 にはあるが JIS X 0208 には無い文字` を分けて報告する。
後者が実務上の落とし穴で、代表は次の2つ。

- `～` U+FF5E FULLWIDTH TILDE — CP932 は 0x8160 をこれに対応させるが、JIS X 0208 を
  厳密に実装した処理系（Java の "SJIS"、ICU の "Shift_JIS"、Python の `shift_jis`）は
  同じバイト列を `〜` U+301C WAVE DASH に対応させる
- `－` U+FF0D FULLWIDTH HYPHEN-MINUS — 同じく 0x817C が `−` U+2212 MINUS SIGN になる

`㎎` U+338E・`㎏` U+338F・`㎝` U+339D・`㎡` U+33A1・`Ⅰ` U+2160・`Ⅱ` U+2161 は CP932 の
拡張領域（NEC特殊文字・NEC選定IBM拡張文字）にあり JIS X 0208 には無い。CP932 の範囲で
往復する限り壊れないが、処理系をまたぐと落ちる。

**R の Windows 版でこの判定をしてはいけない**。win_iconv は `SHIFT_JIS` を CP932 の
別名として扱うため、`iconv(x, "UTF-8", "SHIFT_JIS")` は拡張領域の文字も変換に成功し、
差が見えない。Python の `codecs` は `cp932` と `shift_jis` を区別するので、判定は
Python で行う（このスキルのスクリプトがそうしている）。

## 4. SAS プログラム側の注意

SAS 9.4 の DBCS 版はセッションエンコーディングが CP932 で、`.sas` ファイルも CP932 と
して読む。

- **UTF-8 で保存した `.sas` の実行文に日本語を入れると壊れる**。日本語の末尾バイトが
  直後の ASCII 1文字を飲み込み、`;` が消えて構文が崩れる。`%put` の日本語の直後の
  `%end` がマクロキーワードとして認識されず、マクロがダミーになる形で出る
  （`ERROR: マクロキーワードENDはテキストのように表示されます`）
- `autoexec.sas` を UTF-8 で共有している場合、**実行文は英数字だけで書く**。
  コメントの日本語は `*/` を食わなければ通る
- 既存の `.sas` を編集するときは読み書きともに CP932 で扱う

## 5. 検査を仕様書に残す

方針と確認方法を試験の仕様書に書く。書くのは方針・許容する変数とその理由・検査コマンドで、
**検出件数や文字の一覧は書かない**（データが更新されるとずれる。件数はスクリプトの
出力が正本）。

## 6. このスキルの内部処理

**スクリプトの読み書きはすべてUTF-8で行う。** CP932が出てくるのは2箇所だけで、いずれも
避けられない理由がある。

- CP932依存文字の判定。`ch.encode('cp932')` と `ch.encode('shift_jis')` の成否の差を
  取るのが検査の目的そのもの
- CSVを読むときのフォールバック。UTF-8で読めなかった場合に限りCP932を試す。古い受領
  ファイルのための互換で、**UTF-8が既定**

出力は `sys.stdout.reconfigure(encoding='utf-8')` でUTF-8に固定する。Windowsのコンソールは
コードページがCP932のことがあり、これを入れないと非ASCIIの報告が落ちる
（→ 環境側の知見は llm-wiki の windows-console-codepage-mangles-utf8-handoff）。

**SASプログラム側のCP932はスキルに持ち込まない。** SAS 9.4のDBCS版が `.sas` をCP932として
読むのはSAS側の制約であり、検査するデータの文字コードとは別の話である。Python・Rの
コードは資産として残るので、UTF-8ベースで書く。
