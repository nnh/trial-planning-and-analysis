# trial-planning-and-analysis

作成日：2026-08-22
改訂日：2026-09-14

Ptosh を入力とする臨床試験解析の枠組み。NHO・Ptosh の利用者が使える公開の資産にし、統計家の工数を最小にすることを目的とする。NHOで実施したある試験で実際に組み上げた解析の流れと、そこで見つかった欠陥から一般化した。

枠組みの中心は [pipeline/analysis-pipeline-plan.md](pipeline/analysis-pipeline-plan.md) である。解析の層の定義、フォルダ構成と命名規則、工程の入口条件と出口条件、人の介入ポイント、設計の原則、内部検証の考え方を持つ。他の文書はここを参照し、規則を写さない。どこから読めばよいか分からないときはこれを読む。

## 構成

- [review/](review/README.md) — 立案時レビュー。研究計画書（PRT）・統計解析計画書（SAP）・図表案・電子症例報告書の構造定義（Ptosh の JSON）を対象に、工程ごとに手順・機械検査・蓄積の3点セットを持つ
- [pipeline/](pipeline/README.md) — 解析の流れと層の定義、フローチャート、CDISC 適合性検証・ARS の調査
- [skills/](skills/README.md) — 実行できるスキル（Claude Code の Skill 形式）
- [templates/](templates/README.md) — 雛形の CSV・JSON
- [examples/](examples/README.md) — 部品をどう並べるかの見本。読んで書き換えるためのもので、実行しない
- [findings/](findings/README.md) — 工程ごとの欠陥事例の蓄積
- [trials/](trials/README.md) — 試験を1本通すごとに残す通過記録

新しい試験のリポジトリを起こし、固定データを受け取れる状態に立つまでの手順は [starting-a-new-trial.md](starting-a-new-trial.md) が持つ。枠組みを回す端末を1台立てる手順は [setting-up-a-machine.md](setting-up-a-machine.md) が持つ（macOS と Windows の両方）。次の試験に入る前に片づけるものは [action-items.md](action-items.md) が、枠組み自体を直した日ごとの記録は `docs/work-logs/` が持つ。

層をまたぐ解析の生成・検査スクリプト本体（宣言駆動の図表描画、トレーサビリティ索引の生成など）は [pipeline/scripts/](pipeline/README.md#scripts) に置く。受領CSVからSDTM・ADaM・ARD・図表を作る試験固有の実装（疾患固有のエンドポイント計算ロジックを含む）は、複数試験を通して共通部分が見えてくるまで対象外とする。

## 持たないもの

生データ・被験者単位のデータ・実行ログ・出力は持たない。図表の表題・水準の表示名のように試験固有の語彙を持つファイルは、雛形だけを置き中身は空にする。

一般化の元になった試験の名前も、現在のファイルには残していない。過去のコミットに残っているものの扱いは [history.md](history.md) が持つ。

## 3点セットと育つ仕組み

各工程の3点セットは、手順（人が判断する項目のチェックリスト）・機械検査（規則で判定できる部分をスクリプトへ移したもの）・蓄積（その工程で見つかった欠陥を型として残すファイル）である。3点セットが揃うと、判断の要る項目だけが人に残り、規則で判定できるものは自動で拾われ、拾えたものが次の試験へ引き継がれる。

蓄積を機械へ寄せる判定は次の順で進める。初出は欠陥事例に型として書くだけで機械化しない。2試験目で同じ型が出たら機械検査の規則にできるか見る。3試験で同じ手順を踏んだらスキルにする。規則が3試験続けて0件なら落とす候補にする。
