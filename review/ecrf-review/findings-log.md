# eCRF 設計の欠陥事例

作成日：2026-08-12
改訂日：2026-08-22

これまでの試験で見つかった欠陥を型として残す。次の試験で同じ箇所を見るための蓄積であり、レビューのたびに追記する。各項目は、何が起きたか・どう見つけるか・出どころの順に書く。

出どころの試験名は匿名化し、試験A・試験F・試験G と表記する（同じラベルは同じ試験を指す。[../planning-review/findings-log.md](../planning-review/findings-log.md) の試験A・B・C・D とは別の割り当てである）。

## 構造の欠陥

### 参照フィールドの参照先シート違い

参照フィールドを持つシートを複製して新しいシートを作ると、参照先のシート名が自動では置き換わらない。試験A では複製先の4項目が元シートを参照したままになり、60例全例の検査試料・採取日・実施機関・定量域下限が別シートの値になっていた。研究終了後の解析段階で判明し、解析側で補正した。

構造定義の全フィールドから参照型を抽出し、参照先のシート名が自シートと一致するかを見れば設計時点で検出できる（機械検査 R02）。データからの検出は、正常な設計との区別が難しく確実でない。

出どころ：試験A（2026-08-09）

### シートグループ未割り当て

シートが表示順の定義には存在するのに、どのシートグループにも割り当てられていない状態。試験G では5年時点の最終転帰報告が該当した。テストデータにはレコードがあるため画面上は表示されており、データを見るだけでは気づけない。設定漏れであれば、その時点の転帰が収集できず、生存期間の更新集計に直結する。

出どころ：試験G（2026-08-10、機械検査 R01）、試験A（2026-08-22、同 R01 で2件）

### 後から追加したシートのグループ割り当て漏れ

構築の終盤に追加したシートは、シートグループへの割り当てだけが抜けやすい。試験F では中央検査のリンパ球サブセット解析シート3枚（移植後60日・180日・365日）が、追加から2週間後のエクスポート時点でどのグループにも属していなかった。中央検査シートは参加施設ではなく中央診断施設のユーザが入力するため、施設側の入力テストでは気づけない。

同じ試験のバリデーション作業メモで「シートグループ設定」の確認工程が未実施のまま残っていた。機械検査 R01 はこの工程の代替になる。追加日の新しいシートから先に見る。

出どころ：試験F（2026-08-12、機械検査 R01）

### 中央検査の結果が EDC の外にある

中央検査や委託検査の結果を、EDC ではなく指定の報告書で研究代表医師に提出する運用にすると、SAP に図表案があってもデータが解析用データセットに入らない。試験F のキメリズム解析が該当した。PRT は必須検査と定め、SAP には図表案があるが、EDC への収集は会議で「追加不要」と決まっていた。

PRT の検査一覧と SAP の図表案を、eCRF のシート一覧だけでなく「どこに結果が届くか」の観点で突き合わせる。EDC 外の経路があるなら、統合方法を SAP に書かせる。

出どころ：試験F（2026-08-12）

### 同じイベントを個別報告シートと有害事象シートの双方で収集

イベントごとの個別報告シート（発生日・重症度・転帰を持つ）と、期間内の最悪グレードを集める有害事象報告シートの両方に、同じ事象が入っていることがある。試験F では心不全・非感染性膀胱炎・SOS・真菌・EBV-LPD の5系統が該当した。

累積発生関数の推定には日付を持つ個別報告シートを使うことになるが、SAP が「安全性の評価で定義したイベント」としか書いていないと実装者が取り違える。個別報告シートを持つイベントは、有害事象シート側にも同名の項目がないかを必ず確認する。

出どころ：試験F（2026-08-12）

### 疾患ごとの選択肢の非対称

疾患で分けない共通シートとして運用する設計でありながら、効果判定は全疾患分そろっているのに、治療内容の選択肢は一部疾患のものしか無い、という非対称。試験G では2つの疾患区分の症例が2コース目や地固め療法に進んだ場合、効果判定は入力できるが治療内容を記録できない。治療コース数を数える集計も成立しなくなる。

シートを疾患共通にする判断と、選択肢を疾患別に作る判断が別々に行われると起きる。共通シートは、シート内のすべての選択肢について対応疾患がそろっているかを確認する。

出どころ：試験G（2026-08-10）

### 同一情報を持つシートの複数化

観察期間が長い試験で、同じ報告を時点ごとに別シートで収集すると、症例あたり複数レコードになる。試験G では3年時点と5年時点の最終転帰報告が2枚あり、両方にレコードを持つ症例、片方だけの症例が混在する。転帰の確定には症例単位で両方を参照して最新を採る処理が要る。

シートを分けること自体は正しい設計（時点で収集項目が違う）だが、SAP に採用ルールを明記しないと実装者が取り違える。

出どころ：試験G（2026-08-10）

## SDTM 変数の欠陥

いずれも構造定義から機械的に判定できる。CDISC 担当者が返していた指摘表と同じ型。

### 長さの制約違反

TESTCD は8文字以内、TEST とSDTM 変数ラベルは40文字以内。試験G では染色体異常の記法による TESTCD が9文字、染色体異常や予後分類の TEST が41〜58文字だった。日本語ラベルは40文字を超えやすい。

超えたまま残す判断もありうる（試験G では説明文をそのままラベルにした4項目を修正不要とした）。その場合は判断の記録を残す。残さないと次のレビューで再び挙がる。

出どころ：試験G（2026-06〜07、機械検査 R03・R04・R05）

### TESTCD の取り違え

シートを複製して検査項目を作ると、TESTCD だけ元のまま残ることがある。試験G では別の遺伝子変異の TESTCD が、複製元の遺伝子のものになっていた。同一シート・同一レコード内で TESTCD が重複していないかを見れば検出できる。

出どころ：試験G（2026-06-19、機械検査 R06）

### 選択肢マスタ内のラベル重複

別のコードに同じ表示ラベルが付いている状態。入力者は画面上で区別できず、どちらが選ばれるかで格納値が割れる。試験G では染色体異常の記法・抗体名・単位表記などが該当した。多くは共通テンプレート側の重複であり、試験側で直しても、テンプレートを再取り込みすると戻る。

本試験で実際に固定値として使われているコードが片方だけなら、その試験のデータは割れない。機械検査は使用状況を添えて出すので、対応の要否はそれで判断する。

出どころ：試験G（2026-07-22、機械検査 R07）

### 日付バリデータの欠落

日付フィールドに前後関係・範囲のバリデータが無いと未来日が入る。上限に当日を置くのが既定。移植後の生着日のように、他の日付を下限にすべき項目もある。

出どころ：試験G（2026-06-19、機械検査 R09）

### 数値バリデータと実データの不一致

上下限を設定していても、画面を通さない投入経路（データインポート等）では効かない。試験G のテストデータでは、下限0のはずの握力と観察開始時の使用薬総数が、同一症例でともに `-1` だった。バリデータの設定を確認するだけでは足りず、実データの値域と突き合わせる。

片側しか設定していない項目も残りやすい。上限の無い件数項目は、桁を打ち間違えた入力を通す。

出どころ：試験G（2026-08-10、機械検査 R10）

### 論理式のフィールド参照ミス

論理式が別のフィールド番号を指している、記法が混在している（`field5` と `f2`）、一時保存時に未定義のメソッドを呼ぶ、といった誤り。試験G の構築中に複数回発生した。入力テストで初めて出るものもあるため、機械検査だけでは拾いきれない。

論理式の最大値と最小値が逆転しているものもあった。範囲を設定した項目は、上限と下限の大小を確認する。

出どころ：試験G の CRF 構築記録（2026-06〜07）

## 解析可能性の欠陥

### 導出に必要な対応表の欠落

診断名が疾患マスタのコードで格納され、解析で使う疾患区分への対応表が無い状態。試験G では診断コードから解析用の疾患区分への変換表が入手できておらず、SAP に導出規則を書けなかった。

割付コードを疾患区分の代わりに使わない。割付は割付の記録であり、欠測する症例がある。

出どころ：試験G（2026-08-10）

### 層別因子の取得元が登録票と実施報告の2か所にある

割付の層別因子は登録時点の予定値で入力し、同じ内容を実施報告でも収集する設計になることがある。試験F ではドナーの血縁・非血縁が症例登録票（予定されたドナー）と移植報告（実際の移植）の双方にあり、割付の調整因子式は登録票側を参照していた。

ITT 原則では割付に用いた登録票側の値で調整するが、SAP が「割付の際の層別因子によって調整」としか書いていないと、実装者が実際の移植側を使う余地が残る。割付の調整因子式を eCRF Spec の allocation シートで確認し、参照先のシートとフィールドまで SAP に書かせる。

出どころ：試験F（2026-08-12）

### 起算日・イベント日の取得元の曖昧さ

DM に治療開始日・終了日・死亡日を持たない設計では、生存期間の起算日とイベント日を他ドメインから導出する。導出はできても、SAP に取得元をドメインと変数名まで書かないと、実装者が別の日付を使う余地が残る。

出どころ：試験G（2026-08-10）

### 適格性の判定結果の欠落

選択基準・除外基準の判定項目が SDTM にマップされず、IE ドメインも無いと、解析対象集団の導出根拠をデータ側に残せない。FAS の定義が「重大な違反の症例を除外した集団」であっても、除外の根拠がデータにない。

出どころ：試験G（2026-08-10）

### 評価日を持たない横断シート

一定時点の横断的評価では、評価日をあえて持たせない設計がある（日付を持たせると許容範囲から外れる評価が生じ扱いが煩雑になるため）。設計としては妥当だが、SAP または入力手引きに「許容範囲の遵守は検証しない」と一文残さないと、実装者が存在しない評価日を探す。

出どころ：試験G（2026-08-10）

### 曝露の有無で生存を比較する設計

観察期間中の使用有無で生存曲線を比較する解析は、登録時点の情報ではないため不死時間バイアスを含む。方針として確定しているなら、探索的な比較であり因果的な解釈をしない旨を SAP に一文添えておく。

出どころ：試験G（2026-08-10）

## 文書間の不整合

### 版の呼称ゆれ

同じ分類の版が資料ごとに違う呼び方になる。試験G では疾患分類の版が資料ごとに4通りの書き方で書かれていた。疾患ごとに参照する版が異なる構造（適格性は最新版、患者背景は疾患別）だと特に混乱する。

### 同義項目の併存

「高脂血症」と「脂質異常症」のように同義の選択肢が並ぶと、入力者によってどちらを選ぶかが割れる。集計時に合算するのか区別するのかも決まっていない。PRT・SAP・eCRF の3つすべてに入り込むため、1か所を直しても残る。

### ラベルが指す範囲の誤解

「上記◯◯の総数」のようなラベルは、直前に並ぶ選択肢の該当数と読まれる。試験G の「上記観察開始時の使用薬（種類）の総数」は、実際には限定された分類に限らない全処方薬の種類数だった。施設が別の解釈をすると定義が施設間で割れる。入力手引きに定義を明記する。

出どころ：いずれも試験G（2026-08-10）

## レビュー側の誤り

### 変数名を持たないマッピングで検査が異常終了する

構造定義には、ドメイン接頭辞だけを指定して変数を割り当てていない項目がある。`audit_ecrf_json.py` はこれを `None` のまま扱っていたため、1件でも該当があると R03 の途中で落ち、以降の規則が1つも走らなかった。検査が0件を返したのではなく、走っていなかった。2026-08-22 に飛ばして続ける形へ直した。

新しい試験の JSON にかけるときは、終了コードと規則ごとの件数を必ず見る。件数が出ていることが、その規則が走った証拠になる。

出どころ：試験A（2026-08-22）

### 構造定義だけで判断して実データで裏を取らない

試験G の初回レビューで挙げた24件のうち3件は、こちらの検査の誤りだった。原因はいずれも、構造定義だけで判断して実データで裏を取らなかったこと。

- 構造定義に選択肢が現れない型のフィールド（疾患マスタ参照型）を見落とし、「その情報を持つ項目が無い」と判断した
- 選択肢の名称に埋め込まれた区分を読まず、「分類が曖昧」と判断した
- 項目のラベルから意味を推測し、実データで突き合わせずに「層別が成立しない」と判断した

指摘に上げる前に、テストデータで裏打ちする。裏が取れないものは、指摘ではなく確認事項として出す。
