# eCRF 設計レビュー

作成日：2026-08-12
改訂日：2026-08-22

EDC 固定前に、eCRF が PRT・SAP のとおり構築され、解析に必要なデータが取れる形になっているかを確認するための一式。試験に依存しない汎用資産として、ここを正本にする。

- [checklist.md](checklist.md) — レビュー本体の手順とチェック項目
- [findings-log.md](findings-log.md) — 過去に見つかった欠陥の型。次の試験で同じ箇所を見るための蓄積
- [audit_ecrf_json.py](audit_ecrf_json.py) — eCRF 構造定義 JSON の機械検査

## 位置づけ

CRF の品質は、これまで次の重なりで担保してきた。

- データマネージャによる構築と、CRF 構築記録への逐次記録
- 構築確認者による確認
- CDISC 担当者による CDISC 変数の確認
- バリデーション（EDC 仕様書の確認と入力テスト）
- 研究代表者・参加施設によるレビュー
- 統計解析側による設計レビュー

このうち CDISC 担当者の工程は、支援者個人の知識に依存しており、担当者が代わると失われる。ここに置く一式は、その工程のうち規則で判定できる部分を機械検査に移し、判断が要る部分をチェックリストに書き下したもの。担当者を確保できるかどうかに関わらず、統計解析側で同じ検査を回せる状態にすることが目的。

## 実施の時期

- EDC 固定の前。指摘が構造の変更を伴うため、固定後では直せない
- 構造定義を再エクスポートしたとき。前回の指摘が反映され、新しい欠陥が入っていないかを見る
- 中間解析・データ固定の前。実データが増えた状態で、バリデータの効きを確かめる

試験A では参照フィールドの設定誤りが研究終了後の解析段階で判明し、60例全例の採取日・実施機関が別シートの値になっていた。構造定義を機械検査すれば設計時点で検出できた欠陥だった。

## 成果物

試験リポジトリの `docs/ecrf-design-review-YYYYMMDD.md` に次を書く。

- 検査対象（資料の版・日付・所在）
- 指摘（重要・中程度・軽微に区分し、根拠と検証手順を添える）
- 対応の区分（データセンターへの確認／PRT の改訂／SAP への明記／入力手引きへの記載）
- 確認により解消した論点と、その理由

最後の「解消した論点」を残すことが重要。同じ検査を次に回すと同じ項目が再び挙がるため、理由を残しておかないと毎回同じ照会を繰り返す。試験G では初回に挙げた24件のうち11件がこれに当たった。
