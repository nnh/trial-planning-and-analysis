# eCRF 設計レビュー チェックリスト

作成日：2026-08-12
改訂日：2026-08-22

試験G のレビュー（2026-08-10）と、試験A のデータ固定後に判明した不備を踏まえて作成。欠陥の実例は [findings-log.md](findings-log.md) を参照。

## 1. 資料の収集

依頼から入手まで日数がかかるため、レビュー着手の2週間前には依頼を出す。

必須の6点。

- 研究計画書（PRT）。版と承認日を控える
- 統計解析計画書（SAP）。ドラフトで構わないが版を控える
- aCRF（Annotated CRF）。シート枚数を控える
- eCRF 構造定義 JSON。EDC からのエクスポート。機械検査の入力になる
- SDTM テストデータ一式。全ドメイン、テスト症例を含むもの
- Define XML

あるとレビューが通る4点。無いまま進めると照会の往復が増える。

- eCRF 要件定義書。データマネージャが構築の根拠にしている表
- CRF 構築記録・CRF feedback。設計判断の経緯が入っており、「なぜこうなっているか」の照会を減らせる
- 疾患・診断名のコード対応表。診断名がコードで格納される場合、これが無いと疾患区分を導出できない。試験G で不足し、SAP の導出規則が書けなかった
- バリデーション計画書・報告書。入力テストで何をどこまで見たかがわかる

資料の版が食い違うとレビューが無効になる。6点すべて同じ時点のエクスポートであることを最初に確認する。

資料は組織の文書管理システム（Box 等）にあり、構造定義 JSON・aCRF・Define XML・バリデーション関係の置き場は試験ごとに確認する。

未キャッシュのフォルダは、初回のディレクトリ一覧だけが `Permission denied` になることがある。オンデマンド同期のストレージでは同じコマンドをもう一度実行すれば通ることが多い。権限の問題ではない場合、個別のファイルはパスを直接指定すれば一覧を経ずに読める。

## 2. 機械検査

構造定義 JSON に対して次を実行する。

```
python audit_ecrf_json.py <構造定義JSON> --severity warning
```

規則と、その規則が拾う欠陥は次のとおり。

- R01 シートグループ未割り当て。表示順にあるのにどのグループにも属さないシート。設定漏れなら、その項目が収集できない
- R02 参照フィールドが他シートを参照。シート複製時の置換漏れ。試験A 型の欠陥
- R03 TESTCD が8文字超。CT 規約違反
- R04 TEST が40文字超
- R05 SDTM 変数に紐づくフィールドのラベルが40文字超。SAS XPT の上限
- R06 同一シート・同一レコードで TESTCD が重複。検査項目の取り違え
- R07 選択肢マスタ内で表示ラベルが重複。入力者が区別できず格納値が割れる
- R08 同一シート内で入力フィールドのラベルが重複
- R09 日付フィールドに日付整合バリデータなし。未来日が入る
- R10 数値の範囲バリデータが無い、または片側のみ
- R11 SDTM 未マップの入力項目。分岐制御用なら正しい。解析に使う値が紛れていないかを見る
- R12 無効化された選択肢を含むマスタ。PRT・SAP が要求する値が落ちていないかを見る

`--severity warning` で判断が要るものだけに絞れる。`--format tsv` で表計算に貼れる。

info は件数が多く、そのすべてが欠陥ではない。R08・R11・R12 は設計上の意図があることが多いため、初回だけ通しで見て、以降は差分だけを見る。

機械検査で0件でも設計が正しいことにはならない。以下の突合は人が行う。

## 3. 実データでの裏打ち

構造定義だけで判断すると誤った指摘を出す。試験G のレビューで挙げた指摘のうち3件がこれに当たった。指摘に上げる前に、必ずテストデータで裏を取る。

- 構造定義に現れない項目がないか。疾患マスタ参照型のフィールドは選択肢が JSON に含まれない。試験G では、そのために「疾患区分を取得できる項目が無い」と誤って判断した
- 選択肢の名称に区分が埋め込まれていないか。「その他の強力化学療法」のように、名称の一語で分類が決まっていることがある
- バリデータの範囲と実データの値域が一致するか。試験G では下限0のはずの握力と使用薬総数が、テストデータで `-1` だった。画面を通さない投入経路があると、バリデータは効かない
- 数値の結果値をドメイン横断で走査し、範囲外の値を洗う
- 項目間の整合。同一シートで共通のはずの値（採取日など）が症例間でばらついていないか。試験A の参照フィールド不具合はこの気づきから発覚した

## 4. PRT・SAP との突合

SAP の図表案と PRT のスケジュール表について、全項目を eCRF と突き合わせる。項目の有無より、どの症例に・どの時点で開くかに欠陥が集中する。

- SAP の各図表に必要な項目が、必要な時点で収集されるか
- PRT スケジュール表の各列に対応するシートがあるか。逆に、eCRF にあって PRT に無いシートはないか
- 疾患別・治療別に開くシートの割り当てが、全疾患で対称か。効果判定は全疾患そろっているのに治療内容は一部疾患しか選べない、といった非対称が起きやすい
- 主要評価項目の起算日とイベント日の取得元が確定するか。ドメインと変数名まで特定し、SAP に書けるか
- 解析対象集団の導出根拠がデータに残るか。適格性の判定結果が SDTM に出ない設計だと、FAS の導出根拠を残せない
- 層別・サブグループに使う区分が、単独の項目から導出できるか。割付コードは割付の記録であり、疾患区分の情報源にしない
- 同一の情報を持つシートが複数ある場合、どれを採用するかの規則が決まるか。転帰報告が2枚あると症例あたり複数レコードになる
- 版の呼称、同義項目、ラベルの表現が資料間でそろっているか

## 5. 指摘の確定

- 重要・中程度・軽微に区分する。区分の基準は、解析が成立しなくなるか、解釈が割れるか、表現の問題か
- 対応先で分ける。データセンターへの確認、PRT の改訂、SAP への明記、入力手引きへの記載
- データセンターと統計解析責任者に照会し、設計上の意図と判明したものは指摘から外す。ただし削除せず、解消した理由を記録に残す
- 自分の検査の誤りだったものも記録に残す。次に同じ誤りをしないため

## 6. 記録

- レビュー結果を試験リポジトリの `docs/ecrf-design-review-YYYYMMDD.md` に残す
- 積み残しを `action-items.md` に、未解決の論点を `issues.md` に転記する
- 汎用化できる欠陥の型を [findings-log.md](findings-log.md) に追記する。ここに書かなければ次の試験で同じ検査を思いつけない
