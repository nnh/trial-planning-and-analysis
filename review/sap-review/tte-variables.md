# 生存時間解析の変数命名規約

作成日：2026-08-09
改訂日：2026-08-22

## 概要

全試験共通。時間-イベント（time-to-event）解析の変数を CDISC ADaM に準拠して命名・定義する。2026-08-09 に統計解析責任者の判断で、打ち切りフラグの向きを CDISC 準拠へ切り替えることを決めた。これ以前に作成した試験のプログラムは逆の向きを使っているため、混在期間の事故を防ぐことが本規約の主目的である。

## 打ち切りフラグの向き

`CNSR` は 0 = イベント発生、1 = 打ち切り。CDISC ADaM Implementation Guide の規定であり、以後の全試験でこれに統一する。

```sas
proc lifetest data=adtte;
  time aval * cnsr(1);   /* 1 が打ち切り */
```

### 既存試験は逆である

2026-08-09 より前に作成した試験（試験E 等）のプログラムは、イベント=1・打ち切り=0 で書かれている。同じ 0/1 でも意味が反転するため、次のいずれかに該当する作業では必ず向きを確認する。

- 既存試験のプログラムを新しい試験へ流用するとき
- 複数試験のデータセットを横断して集計するとき
- 既存試験のプログラムを改修するとき
- `proc lifetest` の `censor()` に渡す値を書くとき

向きの取り違えは ERROR も WARNING も出さず、生存曲線が上下反転した結果だけが出る。ログでは検出できないので、変数定義を目で確認する以外に防ぐ手立てがない。生存時間解析の変数を扱う作業に着手するときは、この点を統計解析責任者に確認する。

## ADTTE の標準変数

time-to-event は ADTTE（BDS 構造）で縦持ちにする。エンドポイントごとに変数を増やすのではなく、`PARAMCD` で区別してレコードを増やす。

- `PARAMCD` — パラメータコード（`EFS`・`OS`・`RFS` 等）
- `PARAM` — その説明
- `STARTDT` — 起算日。エンドポイントごとに異なるため必ず持つ
- `ADT` — イベント発生日または打ち切り日
- `AVAL` — 期間。既定は `ADT - STARTDT + 1` の日数
- `AVALU` — 単位（`DAYS` / `MONTHS` / `YEARS`）
- `CNSR` — 打ち切りフラグ（0 = イベント、1 = 打ち切り）
- `EVNTDESC` — イベントの内容
- `CNSDTDSC` — 打ち切り理由
- `SRCDOM` / `SRCVAR` / `SRCSEQ` — 値の由来

月数・年数は `AVAL` の単位を変えた別レコードとして持つか、解析時に日数から換算する。同じ期間を単位違いで複数の変数に持たせない。

## 1症例1行のデータセットでの命名

ADaM の縦持ち変数名はそのまま使えないため、スポンサー定義変数として接尾辞規則に従って命名する。8文字以内、アンダースコアは使わない。

エンドポイント接頭辞（`EFS`・`OS`・`RFS` 等）に次を付す。

- `STDT` — 起算日（ADTTE の `STARTDT`）
- `DT` — イベント/打ち切り日（`ADT`）
- `DY` — 期間・日数（`AVAL`）
- `CNSR` — 打ち切りフラグ（`CNSR`。向きは上記に従う）
- `DESC` — イベント内容（`EVNTDESC`）

例：`EFSSTDT`・`EFSDT`・`EFSDY`・`EFSCNSR`・`EFSDESC`。

接頭辞が長く8文字に収まらない場合は接頭辞を短縮する（`MEVNTCNSR` は不可、`MEVCNSR` とする）。

## 期間の計算

`AVAL` は `ADT - STARTDT + 1` とする（起算日を1日目と数える）。試験内で一貫させ、既存の検算表が別の定義で作られている場合は検算表側を作り直す。

## イベント判定の検証

イベント判定は候補日が複数あり、優先順位・同日の処理・欠測の扱いが絡むため、実装が正しくても判定が期待と違うことが起きる。結果の数値だけを見て正しさを判断しない。次を必ず行う。

### 判定根拠を残す

各症例について、イベント候補日のすべてと、その出所（ドメイン・変数・該当レコード）を中間データセットに残す。採用した日付だけでなく、採用しなかった候補日も残す。どの候補が選ばれ、なぜ他が選ばれなかったかを後から追跡できる状態にする。

### 怪しい症例を機械的に検出する

論理的にあり得ない、または判定が割れやすいパターンを列挙して自動で拾う。件数が0であることを確認し、0でなければ症例ごとに中身を見る。最低限、次を見る。

- イベント日が起算日より前
- 打ち切り日がイベント日より前、または最終追跡日より後
- イベント候補日が複数あり同日（優先順位のtie-breakが効いている症例）
- 到達フラグと到達日の不整合（フラグはYだが日付が欠測、逆も）
- エンドポイント間の矛盾（無イベント生存期間が全生存期間を超える等）
- 死亡日を持つのに死因ドメインにレコードが無い、またはその逆
- イベントの根拠レコードが同一症例に複数存在する

### 症例経過をレビューできる形で共有する

怪しい症例が検出されたら、数を報告するだけで終わらせない。該当症例の経過（各ドメインの関係するレコードを時系列に並べたもの）を一覧にして統計解析責任者へ渡し、レビューを受ける。判定ロジックの修正が必要か、データ側の問題かは、統計解析責任者が判断する。

検出されなかった場合も、全症例の判定根拠一覧（起算日・イベント日・イベント種別・期間・打ち切り理由）は出力して残す。手追跡による確認（数例を原資料まで遡る）の土台になる。

## 接尾辞の一般規則

ADaM の規則をそのまま用いる。

- `DT` — 日付（SAS 日付値）
- `DTM` — 日時
- `DY` — 相対日（基準日を day 1 とする study day）
- `FL` — Y/N のフラグ
- `TM` — 時刻

解析対象集団フラグ（`FASFL`・`SAFFL`・`PPSFL`）もこの規則に従う。
