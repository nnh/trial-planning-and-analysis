# 統計解析計画書レビュー観点

作成日：2026-08-10
改訂日：2026-08-22

## 概要

全試験共通。統計解析計画書（SAP）を固定する前にレビューする観点を定める。試験A の SAP レビュー（2026-05〜07）と、固定データでの実装着手時に判明した齟齬（2026-08-09）から、試験に依存しない形で抽出したもの。

SAP の誤りは、固定後に見つかると修正手続きが重い。一方で SAP レビューの時点ではまだ固定データが無く、実データで裏を取れない項目が残る。本規約は「固定前に必ず潰す項目」と「固定後に実データで確認する項目」を分けて示す。後者は [data-verification.md](data-verification.md) に続く。

## 目的

SAP の記載のうち、実装段階で解釈が割れる箇所・データで埋まらない箇所を、固定前に洗い出す観点を定める。

## 適用範囲

- 統計解析計画書の固定前レビュー、および改訂時のレビュー
- 対象外：研究計画書そのもののレビュー、統計手法の妥当性の検討

## 役割と責任

- 統計担当：本観点でレビューし、指摘を修正前後の対比で提示する
- 統計解析責任者：指摘の採否を判断し、SAP 本体へ反映する
- 研究責任医師：臨床的判断を要する論点を決定する

## 手順

### 4.1. 研究計画書との網羅性を突合する

研究計画書の評価項目の章と統計解析の章を読み、SAP に対応する記載があるかを1項目ずつ確認する。研究計画書にあって SAP に無い項目は、意図的な省略か抜けかを確認する。

実例：累積再発率と非再発死亡率が研究計画書にあり SAP に無かった。主要評価項目の成功基準（信頼区間下限が閾値を上回る）が研究計画書にあり SAP に無かった。サブタイプ別のアウトカム比較が研究計画書にあり SAP に無かった。いずれも固定前に追加した。

### 4.2. 解析対象集団フラグが確定しているか確認する

外部データとして受け取る採否情報が、全例同じ値のまま（例：全例 'Y'）になっていないかを見る。テストデータ段階では暫定値が入ったままのことがある。

確定していない場合、「解析対象：FAS／PPS」と書かれたほぼ全ての表の分母が決まらない。固定前の必須項目として扱う。確定手順は [population-flagging.md](population-flagging.md)。

### 4.3. 記載された変数値・コードが実在するか確認する

SAP が操作的定義で名指しする値（ドメイン名・変数名・`--SPID` や `--TESTCD` の値・訪問番号）を、実データで1つずつ照合する。テストデータの段階でも構造は確認できる。

実例：SAP が指定した `LBSPID='pre_transplantation'` は実データに存在せず、実体は別の値だった。この条件を書いたプログラムはエラーを出さず該当0件で通るため、実装後には気づけない。

### 4.4. 数値しきい値が測定法に依存していないか確認する

検査値のカテゴリ分類を数値のしきい値で定義している場合、その検査値が単一の測定法・単位で得られているかを確認する。複数の測定キットや基準が許容されている試験では、スケールの異なる値が同じ変数に混在する。

実例：分子遺伝学的効果の判定を単一の整数しきい値で定義していたが、実データには標準測定の整数値と別キットの百分率（小数）が混在していた。小数値は誤分類される。判定済みのカテゴリ変数（`RS` ドメイン等）がある場合はそちらを優先し、数値しきい値は測定法を限定して適用する。

### 4.5. 集計項目に対応する実データが存在するか確認する

図表案の行項目を1つずつ見て、その粒度のデータが収集されているかを確認する。特に内訳・詳細分類は、CRF がその粒度で収集していないことがある。

実例：死因の集計表が7分類の内訳を持っていたが、収集データは2分類＋自由記載しかなく大半が埋まらなかった。表を簡素化するか、他ドメインから補完する方針を明記するかを固定前に決める。

### 4.6. 変数の格納場所がまぎらわしくないか確認する

同じ概念が複数の変数に分かれて格納されている場合、SAP の記載がどちらを指すか一意に読めるかを確認する。

実例：急性 GVHD の発生有無は `FATESTCD='AGVHD'`（全例 N）に、グレードは `FATESTCD='GRADE'` かつ `FAOBJ='Acute Graft Versus Host Disease'` に格納されていた。前者だけで集計すると全例「無」になる。

### 4.7. 定義の粒度が実装に足りるか確認する

「〜を対象とする」「〜の日数」といった記載が、プログラムで一意に書けるところまで具体化されているかを見る。起算日・分母・判定時点・カテゴリの境界が曖昧なまま固定すると、実装時に解釈が割れる。

実例：早期死亡の起算日が一部の治療相についてしか規定されていなかった。生着不全の判定日数、GVHD 集計の分母が明示されていなかった。

### 4.8. 未完の文・記号の不整合を洗う

文の途中で切れている箇所、章番号の不整合、全角と半角の混在、同じ内容の二重記載を目視で洗う。軽微に見えるが、実装者が判断に迷う原因になる。

### 4.9. 指摘は修正前後の対比で提示する

指摘は「現行の記載」と「修正案」を並べ、根拠となる研究計画書の条項と、実装で参照する変数名を添える。文章での説明だけにしない。修正を反映する人が判断だけで済む形にする。

優先度を付けて示す。プログラム化を妨げるもの（分母が決まらない・条件が実在しない）を最優先とし、表現の統一は最後に置く。

## 固定後に持ち越す項目

固定前のレビューでは潰しきれない項目がある。次は固定データを受領してから確認する（[data-verification.md](data-verification.md)）。

- 研究計画書の条文と実装ロジックの齟齬。条文を逐語で読み直さなければ気づけない
- 実データの値の分布（想定外の値・欠測・判定不能の混入）
- 規定の隙間に落ちる症例（追跡不能例の打ち切り日など）
- 固定前後でのデータの変化
