## 位置づけ

解析が止まる原因は3つに分かれる。統計解析計画書の記述が実装に落とせる粒度でない、電子症例報告書の構造が解析の単位と合っていない、外部データの受領形式が決まっていない。いずれも解析の段階では直せない。計画書と症例報告書は固定済みで、直すには改訂手続きが要り、外部データは提供元との往復に数週間かかる。

止まると何が起きるかは、規模で見ると分かりやすい。試験A では図表案に起因する未決事項が納品直前まで残り、うち4件が解析の再実行を伴う判断だった。1件あたりの手戻りは、決まってから図表を作り直し、突合をやり直し、トレーサビリティ索引と納品パッケージを作り直すところまで及ぶ。

## 対象と正本

レビューの対象は4つある。それぞれ正本が違う。

- 研究計画書 — [checklist-prt.md](checklist-prt.md)
- 統計解析計画書 — [../sap-review/checklist.md](../sap-review/checklist.md)（9観点）。機械で判定できる部分は [audit_sap_structure.py](audit_sap_structure.py)
- 図表案 — [checklist-tlf-shells.md](checklist-tlf-shells.md)
- 電子症例報告書の構造定義 — [../ecrf-review/](../ecrf-review/README.md)

電子症例報告書だけ別立てにしてあるのは、集める資料と実施の時期が構築の工程と重なるためである。ここへ写さない。

統計解析計画書の観点は [../sap-review/checklist.md](../sap-review/checklist.md) が持つ。全試験共通の規約として先に切り出してあるので、ここへ写さない。図表案は同じ文書の一部でありながら別の速度で改訂されるため、独立したチェックリストにしてある。

## 実施の時期

- 研究計画書 — 倫理審査へ出す前。ここで直せないと、以降はすべて改訂手続きになる
- 電子症例報告書 — EDC 固定の前。指摘が構造の変更を伴う
- 統計解析計画書と図表案 — 固定の前。および固定の直前にもう一度、図表案だけを見る

図表案をもう一度見るのは、本文が固まった後も図表案の改訂が続くためである。本文の規定と食い違ったまま固定されると、実装の段になって初めて分かる。

## 資料

集める資料は [../ecrf-review/checklist.md](../ecrf-review/checklist.md)「1. 資料の収集」が正本で、必須6点とあると通る4点を持つ。ここへ写さない。

資料が同じ時点のものであることを最初に確かめる。版が食い違うとレビューが無効になる。統計解析計画書の作成日が研究計画書より前になっている、といった前後関係の矛盾は、それ自体が最初の指摘になる（試験B で実際にあった）。

## 機械検査

```
python audit_sap_structure.py <統計解析計画書のテキストまたは markdown> [--severity warning]
```

規則と、その規則が拾う欠陥は [audit_sap_structure.py](audit_sap_structure.py) の冒頭が持つ。文書の構造だけを見るもので、内容の妥当性は判定しない。0件でも記述が正しいことにはならない。

規則は S01 から S10 の10。`--severity warning` で判断の要るものだけに絞れる。`--format tsv` で表計算に貼れる。`--rule S07` のように規則を指定して絞ることもできる。

手を入れたら [fixture.md](fixture.md) にかけて、10規則すべてが発火することを確かめる。実文書（過去のレビュー結果・作成仕様の md 4本）では error 0件・warning は編集メモの検出が主で、誤検出は出ていない（2026-08-22 時点）。

## 指摘の出し方

指摘ごとに次を書く。文章での説明だけにしない。修正を反映する人が判断だけで済む形にする。

- 該当箇所 — 文書名と節番号
- 問題点 — 何が起きるかまで書く。「定義が曖昧」ではなく「この定義を文字どおり適用すると Unfit 群が安全性解析から丸ごと落ちる」
- 修正前 — 現行の記載の引用
- 修正後（案） — そのまま貼れる文
- 対応先 — データセンターへの確認、研究計画書の改訂、統計解析計画書への明記、入力手引きへの記載のどれか

区分は重要・中程度・軽微の3つ。基準は、解析が成立しなくなるか、解釈が割れるか、表現の問題か。プログラム化を妨げるもの（分母が決まらない、条件が実在しない）を最優先に置き、表現の統一を最後に置く。

## 成果物

試験リポジトリの `docs/planning-review-YYYYMMDD.md` に次を書く。

- 検査対象（資料の版・日付・Box パスまたは file ID）
- 指摘（上の形式で、区分ごとに）
- 確認により解消した論点と、その理由

最後の「解消した論点」を残すことが重要である。同じ検査を次に回すと同じ項目が再び挙がるため、理由を残しておかないと毎回同じ照会を繰り返す。ある試験の電子症例報告書のレビューでは、初回に挙げた24件のうち11件がこれに当たった。

自分の検査の誤りだったものも残す。次に同じ誤りをしないため。

## 記録

積み残しを試験リポジトリの `action-items.md` に、未解決の論点を `issues.md` に転記する。汎用化できる欠陥の型は [findings-log.md](findings-log.md) に追記する。ここに書かなければ次の試験で同じ検査を思いつけない。
