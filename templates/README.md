# 機械可読な正本の雛形

作成日：2026-08-22
改訂日：2026-09-13

新しい試験を始めるときに、`docs/` へ置く CSV と設定の雛形。列だけを持ち、中身は空である。試験固有の語彙（表題・水準の表示名・表番号）は試験ごとに書き起こすもので、他の試験から流用しない。

置き場は試験リポジトリの `docs/` の下で2つに分かれる。実装が動くために要る定義は `docs/metadata/`、実装を見ずに一次文書から起こした受入基準は `docs/validation/acceptance/` へ置く。どちらへ置くかは各節が示す。ファイル名は試験をまたいで揃える。スクリプトがファイル名で参照するため、置いた階層から動かさない。

## trial.json

試験固有の値をここだけが持つ。スクリプトは試験名をコードに書かず、この設定から引く。

- `trial_id` — プログラム名の接頭辞、納品パッケージ名、表題に使う識別子。`<試験ID>_ARD.sas` のように使われる
- `box_path` — データの置き場。Box のルートからの相対で、要素の配列にする。端末ごとに違う Box のルートは実行時に解決する
- `received_define` — 受領 define.xml のフォルダ。受領物の根からの相対で、要素の配列にする。固定データの回とデータセンターが付けたフォルダ名がそのまま出どころの記録になる。define.xml を作る側と、納品パッケージへ写す側の両方が同じ値を読む
- `define` — define.xml の見出しに載る試験の情報。`study_description`（試験の説明。英語）・`protocol_name`（研究計画書の名称）・`originator`（作成者）を持つ。埋めずに生成を回すと止まる。既定値を持たせると別の試験の説明文を載せた define.xml が黙って出来る
- `sap_pdf` — 固定版 SAP（PDF）の在処。`path`（試験管理側のフォルダからファイル名までの配列）・`fixed`（固定した日）・`box_account`（その PDF を持つ Box の環境名）を持つ。解析が使う試験フォルダとは別のツリーにあるので `box_path` からは辿れない。納品パッケージの必須の同梱物で、解決できなければ組み立てを止める

読むのは Python 側が `scripts/boxpath.py` の `trial_id()`・`trial_dir()`・`received_define_rel()`・`config()`、R 側が `ap_common.R` の `ap_trial_config()`。実行の入口（`run-*.py`）と各層の生成・検査はそこを通して引く。

## tlf-index.csv

図表の宣言。1行が1つの図表で、「どの表番号を、どの表示型で、どの解析の結果値から、どの並びで描くか」だけを持つ。表の作り方はここに書かない。

SAS の描画・R の描画・トレーサビリティ索引の生成の3つが同じファイルを読む。宣言の実体はこれ1つにする。

- `seq` — 報告書の並び。駆動ループはこの順に描く
- `lblid` — 表番号。`label-catalog.csv` のキー
- `display` — 表示型。`tab_` で始まれば表、`fig_` で始まれば図
- `analysis_id` — 結果値の出どころ（表示型が解析1件を描くとき）
- `output_id` — 図表グループ（表示型が複数の解析を一括で描くとき）
- `filter` — 結果値の行の絞り込み
- `groups` — 列に並べる群の識別子。区切り文字の順序が並び順の意味を持つ
- `levels` — 行に並べる水準の識別子。同上
- `item_var` — 背景表の行項目に使う列
- `item_label` — 行項目の見出しに使う固定文言のキー
- `vars` — 一覧表が表示する列の並び
- `labels` — 一覧表の列見出しのキーの並び
- `paramcd` — 図が使うパラメータ
- `where` — 図が使う被験者の絞り込み
- `group` — 図を層別する変数
- `blocks` — 複数の解析を行ブロックとして積むときの並び

表示型マクロの引数名はこの列名と同じにする。対応表を持たないことがこの設計の要点で、対応表があると表示型を足すたびに2箇所を直す作業が生まれる。

実装の詳細（データセット名、解決前のマクロ変数）をこのファイルに入れない。入れると片方の系統だけが読める列になる。

## label-catalog.csv

表示文言。表題・副題・脚注・水準の表示名を、言語ごとの対で持つ。プログラムに文言を書かない。

- `kind` — 文言の種類（表題・副題・脚注・水準・固定文言）
- `key` — 参照するキー。表番号や水準の識別子
- `label_en` — 英語の表示名
- `label_ja` — 日本語の表示名
- `order` — 並び順の番号。同じ行項目に属する水準の中での順序
- `visitnum` — 来院計画（SDTM の TV ドメイン）の `VISITNUM`。治療相の水準に与え、並び順の正本にする
- `source` — 出どころ（統計解析計画書の節番号など）
- `note` — 補足

`order` を持つのは枠組みの既定である。並びを表示名の照合順序に任せると文字符号化に依存し、セッションの符号化を変えるだけで並びが変わる。値は1つも変わらないため、系統間の突合でも前後比較でも検出できない（試験実績で12表387セルが該当した）。

`visitnum` を持つのは、治療の実施順を持っているのが `VISITNUM` だけだからである。識別子の文字順や件数の降順で並べると実際の治療順と食い違う。治療相のための専用のマスターファイルは作らず、この列で持つ。識別子を引く先が2つに分かれると同じ事実を2箇所で管理することになる。1つの治療相に与える識別子は1つだけとし、正本は ADaM の `APHASE` とする（[../pipeline/analysis-pipeline-plan.md](../pipeline/analysis-pipeline-plan.md)「図表の並び順を来院計画から決める」）。

言語を増やすときは `label_<言語コード>` の列を足す。

## level-sets.csv

水準の集合。事前に規定された水準を集合として宣言し、集計の層がそこから引く。

- `set_id` — 集合の識別子
- `level` — 水準の識別子。表示名は `label-catalog.csv` が持つ
- `impl_order` — 集計が水準を並べる順
- `display_order` — 表示の並びが集計と違うときだけ埋める
- `note` — 補足

該当0件の水準を行として残すためにこれが要る。割合を併記する表で行が消えると分母が読めず、行が消えたのか水準が存在しないのかも区別が付かない。集計の層に集合を渡せば0件の行が作られ、表示の層は行が無いものを描かずに済む。図表の宣言（`tlf-index.csv`）の `levels` は表示の並びにしか効かないので、そこへ集合を書いても行は増えない。

事前規定の時点（何年後の推定値を出すか）も集合として持つ。数値の並びを表示型の引数に持たせると、集合の宣言が無いため、解析結果メタデータでは事前規定ではなくデータ由来の水準として扱われる。水準の識別子から値そのものを機械的に導ける形（`Y<年>` など）にしておけば、値を持つのはこの CSV の行だけになる。

宣言に無い水準が結果に出たら止める。事前規定の水準だと名乗れるのはこの照合があるからで、検査を付けられない宣言は増やさない。逆に、イベントの起きた時刻のように固定データから決まる水準は集合を持てない。データ由来の水準として残るのが正しい状態なので、残る理由を書いておく。

## variable-map.csv

層ごとの変数の一覧。トレーサビリティ索引が層をまたいで辿るための対応表になる。

- `layer` — どの層の変数か（sdtm・adam など）
- `dataset` — データセット名
- `variable` — 変数名
- `label_en` — 変数ラベル。英語のみとし、日本語は `label-catalog.csv` が持つ
- `length` — 宣言長。文字型の変数だけが値を持ち、数値型は空にする。ADaM ではこの値が define.xml の `Length` になる（実データの最大長からは採らない）。実データの方が長ければ宣言が値を保持できないので、生成が止まる
- `origin` — 由来の区分（収集・派生・規定値など）
- `predecessor` — 前の層のどの変数から来たか
- `crf_sheet` — 症例報告書の帳票
- `crf_field` — 症例報告書の入力欄
- `spec_ref` — 作成仕様のどの節が規定しているか。`<ファイル名> §<節番号>` の形
- `order` — データセットの中での変数の並び。データセットごとに1から振る通番

`spec_ref` は仕様書 HTML への直リンクになる。参照先の実在は検査で毎回確かめる。

このファイルは索引のための対応表であると同時に、変数の属性の正本でもある。ラベル・宣言長・並びを実装が持つと、その実装を持たない側で値を再現できず、系統ごとに採り方が違えばどちらが正しいかも決まらない。二重コーディングの両系統がここから引き、`itemOID` は `IT.<データセット>.<変数>` の規則で組む（[../pipeline/analysis-pipeline-plan.md](../pipeline/analysis-pipeline-plan.md)「変数の属性の正本を宣言に置く」）。

`order` を行の順ではなく列で持つのは、行順に意味を与えると、定義を読むために並べ替えただけで出力が変わるためである。標準が並びを定める層は外部標準の写しを読み、標準が定めない層だけこの列が持つ。

検査は網羅と一致の両方を見る。参照整合だけを見る検査は、成果物にあってこのファイルに無い変数を見つけない。

## timepoint-map.csv

評価時点の対応表。症例報告書の帳票名と、解析上の時点名の対応を持つ。

- `order` — 時点の並び
- `spid` — 症例報告書側の識別子
- `label` — 表示名
- `glabel` — 群化に使う識別子
- `source` — どのドメインから採るか
- `rsparamcd` — 効果判定のパラメータ
- `rsavisit` — 解析上の訪問名

この対応表を持たないと、実装が帳票名を直接読むことになり、対応がプログラムの中にしか存在しなくなる。試験実績では23時点の対応が品質管理プログラムの書式定義の中にしか無く、後から起こした。

## reference-table-rows.csv と reference-values.csv

参考併記の表（自試験の結果と、先行試験の公表値を列に並べる表）の2つ。行の定義と値を分けて持つ。

`reference-table-rows.csv` が表の構造を持つ。

- `order` — 行の並び
- `item` — 行の識別子。値の側とここで結合する
- `label` — 行ラベルの表示名のキー（`label-catalog.csv` を引く）
- `analysis_id` — 自試験の値を引く解析
- `variable_level` — その解析のどの水準を引くか
- `stat` — 引き方。`n_total`（例数）・`pct_n`（割合と分子分母）・`km_ci`（推定値と95%信頼区間）。空にすると見出しの行になり、自試験の列は空欄になる

`reference-values.csv` が公表値を持つ。試験が増えれば行が増える縦持ちにする。

- `trial` — 公表値の出どころの試験
- `item` — 行の識別子。構造の側とここで結合する
- `value` — 公表されている値。書式のまま文字列で持つ（自試験の値と桁を揃えない）
- `note` — 注記
- `source` — 出典（文献・登録番号）

分けるのは、比較する試験が増えても列を増やさずに済ませるためである。構造の側は行の定義だけを持ち、値の側は縦に伸びる。

公表値を解析結果データに置かない。解析の結果ではないものを同じ場所に置くと、二重コーディングの突合の対象に入り、突合できない行が混ざる。

表示型の側に比較対象の試験名を書かないこと。試験実績では実装が他試験の名前を直書きしており、汎用の部品として使えなくなっていた（[../examples/README.md](../examples/README.md)「表示型の判定」）。列の数と見出しは値の側にある `trial` の実値から決める。

## 受入基準

主要評価項目・解析対象集団の条件・図表ごとの期待の3本。置き場は `docs/validation/acceptance/` で、`docs/metadata/` とは分ける。`metadata/` が持つのは実装が動くために要る定義、`acceptance/` が持つのは実装を見ずに一次文書から起こした「こうあるべき」である。実装から起こすと実装の誤りがそのまま基準になり、二重コーディングの両系統が同じ誤りを共有したときに突合が通ってしまう。

この3本がそろっていることは区間1の出口条件に含まれる（[../pipeline/analysis-pipeline-plan.md](../pipeline/analysis-pipeline-plan.md)「区間1 開始前の確定」）。出口条件の本文はそこが持つので、ここへ写さない。

### primary-endpoint.csv

主要評価項目の判定の正本。1行が1項目の縦持ちで、項目名と値の対で持つ。閾値も判定の向きも、実装にも図表の宣言にも書かない。

- `item` — 項目名。どの解析の結果で判定するか、どの時点の値か、閾値、信頼区間の作り方、判定の式、推定値を持つ操作の名前、主要評価項目の呼び名（`endpoint_label`）
- `value` — その項目の値
- `source` — 根拠となる一次文書の節番号

`endpoint_label` だけは雛形に行を置いてある。主要評価項目の呼び名は疾患で変わるため、汎用層のコードは略号を持たず、この行が空なら一般の語で出す。納品パッケージの結論の段が読む。

縦持ちにするのは、要る項目が試験の設計で変わるためである。単群の閾値比較と対照群との比較では項目が違い、列で持つと使わない列が残る。

判定の式を宣言に置くのは、向きを実装に書くと、実装を読まずに向きを確かめられないからである。照合する側は宣言された式で判定をやり直し、記録された判定と突き合わせる。

### analysis-set-condition.csv

解析対象集団と部分集団の選択条件、および期待例数。

- `id` — 集団・部分集団の識別子。図表の宣言・ARD の行・解析メタデータが同じ識別子で指す
- `kind` — 解析対象集団か部分集団か
- `dataset` — 条件を評価するデータセット
- `variable` — 条件に使う変数
- `comparator` — 比較演算子
- `value` — 比較する値
- `n_expected` — 期待例数。解析対象集団だけが持つ
- `note` — 単一の条件では表せないものの説明と、根拠の節

条件の4列を空にした行は「単一の条件では表せない」という宣言で、そのとき `note` が選び方を持つ。条件を空のまま識別子と名前だけにすると、受け取る側は誰を数えたのかを成果物から辿れない。

`n_expected` を持つのは、集団フラグの確定が「条件式で数えた例数が期待例数と一致すること」を出口条件にするためである。一致しない集団は判断票にする。例数の正本はこの列だけで、図表ごとの期待（`display-contract.csv`）へは写さない。あちらは例数ではなく集団の識別子で宣言する。

### display-contract.csv

図表1件ごとの期待。1行が1つの図表で、描き上がったものが宣言どおりかを見る。

- `lblid` — 表番号。図表の宣言（`tlf-index.csv`）と同じキー
- `display` — 表示型
- `n_rows` — 期待する行数
- `row_levels` — 期待する行の水準の並び。水準の識別子で書く
- `ci_method` — 信頼区間の作り方。空欄は「この図表に信頼区間は無い」という宣言
- `analysis_set` — その図表のセルが由来する解析対象集団の識別子
- `data_subset` — 同じく部分集団の識別子
- `source` — 根拠となる一次文書の節番号

`row_levels` を表示文言で書かない。表示文言は一意でなく（1つの文言が2つ以上の水準に付く）、文言から水準を特定できない。加えて、文言を変えるのは表示の判断であり、受入基準の意味がそれで動いてはならない。

`ci_method` の空欄を未記入ではなく宣言として扱う。そう決めておくと、信頼区間のセルを持つ図表で空欄が残っていることを食い違いとして拾える。

行数を宣言するのは、両系統が同じ誤りを共有したときに突合が通るためである。試験実績では、指定5時点を出すはずの時点表19件が曲線の全イベント時点を印字して89行になり、両系統が同じ89行を出したため突合を通った。

## crf-field-map.csv と crf-option-map.csv

症例報告書の対応表2本。帳票・項目・SDTM 変数の対応（`crf-field-map.csv`）と、選択肢セットの値（`crf-option-map.csv`）を分けて持つ。

この2本は手で書かず、電子症例報告書の構造定義から生成する。雛形が列だけを持つのは、生成側が書き出す列の約束を試験をまたいで固定するためである。列名が変わると、索引・トレーサビリティ・図表の実装が同時に読めなくなる。

`crf-field-map.csv` は1行が1項目。

- `sheet_seq` — 帳票の並び。症例報告書の記入順
- `sheet_slug` — 帳票の識別子。SDTM の `--SPID` の実値と同じ
- `sheet_name_ja` — 帳票の表示名
- `field_name` — 項目の識別子
- `field_seq` — 帳票の中での項目の並び
- `field_kind` — 項目の種別。施設が入力する欄・固定値・他の帳票からの参照・見出し・注記
- `field_type` — 入力の型
- `field_label` — 項目の表示文言
- `field_note` — 項目に付く注記
- `invisible` — 画面に出ない項目の印
- `record_label` — その項目が載る SDTM レコードの通し番号
- `sdtm_domain` — そのレコードのドメイン
- `sdtm_variable` — その項目が入る SDTM の変数
- `assigned_value` — 固定値の項目が持つ値
- `option_name` — 選択肢セットの名前。`crf-option-map.csv` のキー
- `reference_field` — 参照の項目が引く先

変数がどのデータセットにあるかという事実は `variable-map.csv` が持つので、ここへ写さない。この対応表が持つのは変数名と、その変数が属するレコードだけである。

`crf-option-map.csv` は1行が1つの選択肢の値。

- `option_name` — 選択肢セットの名前
- `code` — 格納される値
- `label` — 表示名
- `seq` — セットの中での並び

## sdtm_datasets.csv

SDTM のデータセットの一覧とラベル、交換形式と定義文書が使う識別子。

- `dataset` — データセット名
- `label` — データセットのラベル
- `itemGroupOID` — 定義文書の中でそのデータセットを指す識別子
- `studyOID` — 試験を指す識別子
- `metaDataVersionOID` — メタデータの版を指す識別子

ドメインのラベルは標準の版で文言が変わるので、実装へ書かず宣言が持つ。二重コーディングの両系統と定義文書の生成が同じファイルを読む。

ファイル名の区切りだけが他と違う（`_`）。読む側がファイル名で参照しているので、揃えるなら実装と同時に直す。

## sdtm-value-level.csv

SDTM の値水準メタデータ。テストコードごとに名称が決まる対応を持つ。

- `domain` — ドメイン
- `testcd` — テストコード
- `test` — そのテストコードに対応する名称

対象のドメインを列挙で持たない。テストコードの変数と名称の変数の両方を持つドメインという条件が、そのまま対象になる。列挙すると、ドメインが増えたときに列挙の側が取り残される。

この宣言は実データを言い直す形になるので、実データとの照合を検査で毎回見る。宣言に無い値が実データに出たら止める。

## sdtm-codelist-values.csv と sdtm-codelist-mode.csv

SDTM の定義文書で、受領した定義のコードリストを実データへ合わせるための宣言2本。どの変数をどう合わせるか（`sdtm-codelist-mode.csv`）と、合わせた先に載せる値（`sdtm-codelist-values.csv`）を分けて持つ。

`sdtm-codelist-mode.csv` の列。

- `domain` — ドメイン
- `variable` — 変数
- `testcd` — 空なら変数そのもののコードリスト、入っていればそのテストコードの行だけを指す値水準のコードリスト
- `mode` — 合わせ方。受領した選択肢を置き換えるか、足すか
- `note` — そう決めた理由と、規定している仕様の節

`sdtm-codelist-values.csv` の列。

- `domain`・`variable`・`testcd` — 上と同じ指し方
- `value` — コードリストに載せる値

1つにまとめない。合わせ方は変数ごとの判断、値は値ごとの行なので粒度が違う。1つにすると合わせ方が値の数だけ繰り返され、全行が同じ値であることを別途確かめる必要が生じる。2本のドメインと変数の組が過不足なく対応することは、生成側が読み込み時に見る。

合わせ方を実装ではなく宣言に置くのは、これが標準の定義でも実装の都合でもなく、SDTM の層で値の体系を作り直したか症例報告書の選択肢へ足したかという試験固有の判断だからである。実データからは決まらない。

`testcd` の列が要るのは、1つの変数の中でテストコードごとに値の体系が違うことがあるためである。列が無いと、体系の違う値が同じコードリストに同居する。

## codelist-decode.csv

SDTM の定義文書に載せる Decode の対応。受領した定義文書が値と割り当てを持ち、そこにどこにも無い表示名だけをこのファイルが持つ。

- `codelist_oid` — コードリストの識別子
- `coded_value` — 格納される値
- `decode` — その値の表示名
- `source` — 出どころ

値そのものを持たない。値は受領した定義文書と症例報告書の選択肢の対応表にすでにあるので、写すと同じ事実が3箇所になり、受領版との対応関係も失う。差分だけを持つ。

Decode を持たない値は検査が件数を報告する。足すかどうかは都度決める。

## adam-codelist.csv

ADaM の定義文書が使うコードリスト。ADaM には受領した定義文書が無いので、値と表示名の両方をこのファイルが持つ。SDTM が受領した定義文書を正本にして差分だけを宣言するのとは、ここが違う。

- `codelist_oid` — コードリストの識別子
- `codelist_name` — コードリストの名前
- `datatype` — 値の型
- `variables` — このコードリストを当てる変数。空白区切りで、`*` を含むものはパターンとして扱う
- `coded_value` — 格納される値
- `decode` — その値の表示名
- `source` — 出どころ。仕様書の節番号や外部標準の版

1つの識別子が複数行に分かれ、1行が1つの値を持つ縦持ちにする。`codelist_name`・`datatype`・`variables` は識別子ごとに1回書けばよく、残りの行は空でよい。

`coded_value` を `include:` で始めると、値を書かずに他の宣言から引く。同じ水準が表示文言の一覧（`label-catalog.csv`）にあるときに、値を写さないための道である。

`variables` にパターンを書けるのは、フラグ変数のように名前の形で決まる群があるためである。完全一致がパターンより優先し、1つの変数に2つの識別子が当たれば生成を止める。

## analysis-grouping.csv

解析が結果を分ける軸（群）の宣言。1行が1つの水準で、同じ識別子の行が集まって1つの軸になる。

- `grouping_id` — 因子の識別子
- `data_driven` — 事前規定かデータ由来か
- `dataset` — 群を決めるデータセット
- `variable` — 群を決める変数
- `group_id` — 水準の識別子。データ由来の因子では空にする
- `order` — 表示の並び
- `note` — そう決めた理由

表示名の列は持たない。群の表示名は `label-catalog.csv` の `kind=level` が正本で、ARS の生成器も図表もそこを引く。宣言のこちら側にも表示名を置くと同じ文言が2か所になり、片方だけ改訂したときに図表と解析メタデータが違う名前を述べる。宣言の無い水準は識別子がそのまま表示名になる。

`data_driven` は、群が事前に計画で決まったものか、変数の相異なるデータ値から得られたものかを表す。実装が水準を列挙したかどうかではない。事前規定なら水準を並べ、結果はその識別子を指す。データ由来なら水準を持たず、結果は実際の値を指す。

空欄・誤記・因子の中の食い違いを偽と読まない。読めないものは組み立てを止める。分からないものをデータ由来の既定へ落とすと、事前規定の群が黙ってデータ由来を名乗る（逆も起きる）。

水準の集合（`level-sets.csv`）とは混ぜない。混ぜると、全行を群の因子として読む側が水準集合を群の軸として拾う。識別子の名前空間を分けておき、他方の名前で来た行は止める。

表示名を持つ列はここと `label-catalog.csv` の両方にある。どちらを正本にするかを試験の初めに決めて `note` に書く。決めずに両方を埋めると、片方だけを直したときに図表と解析メタデータで表示名が食い違う。

## analysis-purpose.csv

解析の目的と、それがいつ計画されたか。解析メタデータの標準が解析1件ごとに必須とする項目で、結果からは決まらない。

- `output_id` — 図表グループの識別子。この行はそのグループに属する解析すべての既定になる
- `analysis_id` — 解析の識別子。この行は既定を上書きする
- `purpose` — 何のための解析か。主要・副次・探索など
- `reason` — いつ計画されたか。研究計画書での規定・統計解析計画書での規定・データを見てからなど
- `note` — 根拠となる節番号

既定と上書きの2段にするのは、同じ図表グループに属する解析の多くが同じ値を採るためである。解析ごとに全部書くと、1つの変更が行の数だけ散る。

どちらの欄も空のまま通さない。目的を宣言していない解析が宣言済みと見分けが付かなくなるので、欠けていれば組み立てを止める。

## method-code.csv

解析手法の実装を系統ごとに持つ。解析メタデータに載る手法の記述になる。

- `method_id` — 手法の識別子。図表の宣言と ARD が同じ識別子で指す
- `system` — 実装系統
- `context` — その系統の言語名
- `code` — 実際に呼ぶ処理。関数呼び出しそのものか、手法の記述
- `document_id` — 実装の置き場を指す参照文書の識別子（`reference-documents.csv` のキー）

二重コーディングでは同じ識別子が系統の数だけ行を持つ。受け取る側は、どの系統でどう計算したかを解析メタデータから読める。手法の識別子が同じでも系統で書き方は違うので、系統をまたいで1行にまとめない。

実装の中身をここへ写さない。持つのは呼び出しの1行と、実装そのものへの参照である。

## reference-documents.csv

成果物が指す文書の一覧。

- `id` — 文書の識別子
- `name` — 機械が使う名前
- `label` — 表示名
- `location` — 納品パッケージの中での置き場
- `for_reason` — その文書を根拠とする解析の計画時期の値
- `description` — 何を持つ文書か

`for_reason` があるのは、解析の側が持つ計画時期は「いつ計画されたか」を述べるだけで、受け取る側がその主張を確かめられないためである。この列があると、計画時期から根拠の文書を引いて解析に結び付けられる。データを見てから決めたもののように、対応する事前の文書を持たないものはこの列を空にする。

## core-issue-disposition.csv

適合性検証が出した指摘の仕分け。直さずに残すと決めたものを1行ずつ持つ。

- `core_id` — 指摘の識別子
- `disposition` — 扱い。`known` は指摘を残すと決めたもの、`execerror-ok` はルールが実行できなかったことを承認したもの
- `note` — なぜ残すのか
- `ref` — 判断の根拠になる記録
- `ds` — 許容の対象データセット。`;` 区切りで並べる。全ドメインに及ぶときだけ `ALL` と書く

このファイルに無い指摘は未仕分けとして扱う。仕分けの済んだものと済まないものを機械で分けられるのは、残す側を1件ずつ列挙しているからである。件数で「変わっていない」と確かめる作りにすると、指摘が入れ替わっても件数が同じなら通る。

`ds` を持つのは、許容をルールだけで結ぶと範囲が広がりすぎるためである。あるドメインの形式的な指摘を `known` にすると、次のカットで別のドメインに出た本当の欠陥が同じルールに当たって一緒に許容される。対象を書き忘れた行（`ds` が空欄）は許容として扱わない。書き忘れを許容と読むと、この列を足した意味が消える。

未仕分けが残っている場合と、承認していないルールの実行失敗がある場合は、検証の終了コードが 1 になる。

指摘の本文と件数はこのファイルへ写さない。持つのは識別子と、残すという判断だけである。

## release-artifacts.csv

通し実行の段ごとに、その段が作る成果物のうち試験側にしか名前が分からないものの宣言。`run-release.py` が読む。

- `step` — 段の番号
- `path` — 試験フォルダからの相対パス。区切りは `/`
- `note` — 何の成果物か

枠組みは段階1・2・3・4・6 の成果物を知っているが、突合と視覚回帰の出力は試験側のプログラムが決めるので名指しできない。宣言の無い段を `--from` で飛ばそうとすると、実施した記録だけでは同じ回のものだと確かめられないため落ちる。飛ばす予定のある段は宣言しておく。

## received-manifest.csv

受領データのうち、解析が読む現行の入力がどれかの宣言。固定データ検査（`audit_fixed_data.py --manifest`）が読む。

- `file` — 受領データの置き場の直下からの相対名
- `sha256` — そのファイルの指紋。空でもよいが、入れると写し損ないを捕まえられる
- `note` — 抽出日・受領の経緯など

並んだファイルだけを読み、並んでいないファイルが直下にあれば止まる。直下だけを見る規則で旧版の混入は防げるが、写し損ないは防げない。同じ名前の古いファイルが1つ残っても件数は合う。宣言した集合と実在を突き合わせて初めて分かる。

再抽出のたびに書き直す。書き直さないと、宣言が前のカットを指したまま検査だけが通る。

## diff-key.csv

固定前後の差分で、ドメインごとに何で行を結ぶかの宣言。`audit_fixed_data.py --keys` が読む。

- `domain` — ドメイン名
- `key` — キーにする変数。複数は `;` で区切る
- `note` — そのキーで一意になる理由

宣言の無いドメインは照合せず、未評価として残す。推測で結ぶと、結んだ結果が正しいかを後から確かめられない。判定を表す変数（`--OCCUR`・`--STAT`・`DSTERM`・`--ORRES` など）はキーにしない。値が変わった行が別の行になり、変化そのものが見えなくなる。

## delivery-contact.csv

納品物を受け取った側の問い合わせ先。

- `item` — 項目名
- `value` — 値
- `note` — 確かめた方法と日付

値が決まっていなければ行を作らない。空のときに項目名だけを並べて出すと「問い合わせ先は、この一式を渡した担当者に確かめてください」のように文が自分を指す。読む側が実際にたどれる先は渡した担当者そのものなので、値が無いときは案内の側がその1文を出し、このファイルは値が入ったときだけ使われる。

## 使い方

1. 雛形をコピーする。受入基準の3本は `docs/validation/acceptance/`、残りは `docs/metadata/` へ置く。名前は雛形のまま変えない。読み手（`tlf_ops.R`・`tlf_ops.sas`・検査スクリプト）が雛形の名前で探すので、試験ごとに変えると時点別の表示型が読み込みで止まる
2. `trial.json` の2つの値を埋める
3. 区間1で決め切る事項を受入基準へ落とす。`analysis-set-condition.csv` に集団の条件と期待例数、`primary-endpoint.csv` に主要評価項目の判定、`display-contract.csv` に図表ごとの期待を書く。3本とも実装を見ずに一次文書から起こす。この3本を先にするのは、後の工程がここを基準に照合するためで、実装ができてから書くと基準が実装の写しになる
4. 図表案が固まったら `tlf-index.csv` と `label-catalog.csv` を書き起こし、事前規定の水準を `level-sets.csv` へ、結果を分ける軸を `analysis-grouping.csv` へ宣言する。図表案のレビュー（[../review/planning-review/checklist-tlf-shells.md](../review/planning-review/checklist-tlf-shells.md)）を通してから書くと、後から並び順や分母で戻らない
5. 解析メタデータの3本（`analysis-purpose.csv`・`method-code.csv`・`reference-documents.csv`）を埋める。目的と計画時期と参照文書は一次文書から起こし、手法の実装は系統ができた時点で足す
6. 症例報告書の構造定義がそろったら `crf-field-map.csv` と `crf-option-map.csv` を生成する。この2本は手で書かない
7. `variable-map.csv` は層を作りながら埋める。SDTM の層では `sdtm_datasets.csv` と定義文書の宣言4本（`sdtm-value-level.csv`・`sdtm-codelist-values.csv`・`sdtm-codelist-mode.csv`・`codelist-decode.csv`）を、ADaM の層では `adam-codelist.csv` を合わせて埋める
8. 適合性検証を回したら、直さずに残すと決めた指摘を `core-issue-disposition.csv` へ書く
9. 参考併記の表を出す試験だけ、`reference-table-rows.csv` と `reference-values.csv` を埋める。出さない試験ではコピーしない
10. 納品の問い合わせ先が決まったら `delivery-contact.csv` へ入れる

雛形に中身を残さない。表題や水準の表示名を他の試験から流用すると、その試験の語彙が紛れ込む。
